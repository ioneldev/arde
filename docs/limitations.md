# Limitations

What ARDE does not do, and what has not been tested. Most of it comes from the [design](superpowers/specs/2026-11-01-arde-design.md). The writable-mount risk was found later, in a security review of the container experiment. Add to this page when you find a new limit.

## Trust and containers

- **Repos must be trusted.** The repo's code runs in the same container as ARDE and the API key. Removing `ANTHROPIC_*` from child processes limits accidents, but it is not a security boundary: code running as the same user could still read the parent's environment. This is reasoned, not tested.
- **A writable repo mount is an open risk.** The container mounts the local repo so it can write results back. Repo code running in the container could use that mount to tamper with the host repo, for example by planting a git hook that later runs on the host. This must be resolved before the container ships (Task 28 of the plan).
- **The `/data` volume is shared across repos.** The container keeps `ARDE_HOME`, `GOCACHE` and `GOPATH` in one volume, owned by the same user as repo code. Repo A's tests could write repo B's `profile.override.yaml`, the file `extra_test_commands` trusts. This is reasoned, not tested, and must be resolved before the container ships (Task 28 of the plan).
- **Go commands read three settings from the user's `go env` file, and nothing else in it.** ARDE sets `GOENV=off` for every Go command, because that file lives under `HOME` and can hold a `GOFLAGS` with `-toolexec`. Once per process, in the parent, it asks `go env` for `GOPRIVATE`, `GONOPROXY` and `GONOSUMDB`, with the exported values of those three and the user's `XDG_CONFIG_HOME` and `GOENV` so that it looks where the user's own `go` looks, and it passes the answer on as Go gave it. Go decides which value wins and derives `GONOPROXY` and `GONOSUMDB` from `GOPRIVATE`, so a private repo builds and its module paths stay off the public proxy and checksum database. A `GOPROXY`, `GOSUMDB` or `GOTOOLCHAIN` that only the file holds is ignored on purpose, so a poisoned file cannot redirect where modules come from or switch the toolchain: every command runs with `GOENV=off`, and the probe itself runs with `GOTOOLCHAIN=local`, so neither the file nor a `go.mod` above the temporary folder can make it start or download another toolchain. Export anything else you need. An empty exported value counts as not exported. Those three settings can weaken checksum checks for the paths they name, which is why repos must be trusted. If `go env` fails or leaves one of them out, the run stops, because going on without them would send private paths to the public proxy.
- **A link that leads out of a repo stops the run.** Every `GoAdapter` method that takes a repo first walks it and refuses any link whose real path is outside the repo's real path, with exit 2. The message names the link and never its target. This holds for every file, because the Go tool follows links and quotes a `go.mod` it cannot parse. Three things stay outside the gate. `.git` is not walked: a clone cannot put a link there, a hook linked to a shared folder is common, and nothing ARDE runs reads it. A hard link looks like a file, so it passes, and a clone does not create one. The walk runs once, when the method starts, so a link that a test makes during `run_checks` is not seen, and that code could read the same file anyway.
- **A repo cannot choose its toolchain unless you let it.** Every Go command runs with `GOTOOLCHAIN=local` unless you export another value, so a `go` or `toolchain` line in `go.mod` can neither start a program found on `PATH` nor ask for a download. The cost is that a repo that needs a newer Go than the one installed stops with Go's own error, such as `go.mod requires go >= 1.99.0`, and `goinspect` itself needs the Go version in its own `go.mod`. Export `GOTOOLCHAIN=auto` to accept the switch.
- **A relative `PATH` entry is removed from every child's environment.** A child changes folder before it looks for a program, so `.` or an empty entry would find a `go` the repo planted. When nothing absolute is left, `PATH` is left out and the system's default path applies, because an empty `PATH` reads as the current folder.
- **A repo decides its own workspace, and nothing above it can.** Every Go command and `goinspect` run with `GOWORK` set to the repo's own `go.work` when that regular file exists, and to `off` otherwise. Without this, Go looks in every folder above the repo, and a `go.work` planted there chose the code that was built and run. An exported `GOWORK` is ignored.
- **A timeout cannot reach a grandchild that started its own session.** The child and its process group are killed, and ARDE stops waiting. A daemon that a test or an extra command started on its own keeps running.
- **If ARDE itself is killed with SIGKILL, SIGTERM or SIGHUP, a running service is left behind.** The service runner stops the service in a `finally` block, which covers a normal exit, an error and Ctrl-C. SIGKILL gives no code a chance to run, and that will stay so. SIGTERM and SIGHUP leave the service behind too, until the CLI installs its handlers for them in Task 17: Python has no handler for either by default, so no `finally` runs. The service keeps its port and its process group until someone stops it. To find it, look in `ps` for a binary in a folder named `arde-service-` under the temporary directory, and kill its process group.
- **The service gets the grace period only through its leader.** The runner sends SIGTERM to the whole process group, waits up to 5 s for the first process to exit, and then kills the group. A worker that needs longer than its parent to shut down is cut off the moment the parent exits. A service that starts its own session is out of reach of the group, as for any child.
- **A free port is found by binding and closing, so another process can take it before the service binds.** The window is short. A service that loses the race normally exits at once and is reported with its log. If the other process opens the port and answers, the first probe connects to it and the body starts against the wrong process. The service, which could not bind, exits, and the runner reports that as a `ServiceDiedError` with its log when the body ends.
- **A Ctrl-C that lands inside the `Popen` call itself leaves the service running.** The process exists before `Popen` returns its handle, so the runner has nothing to stop yet, and moving the `try` cannot close that. The window is the few milliseconds the call takes. An interrupt anywhere else in the start, the wait, the body or the stop leaves nothing running.
- **The runner connects to `127.0.0.1` only.** A service that listens on `::1` alone is not found, and fails with the timeout error, which now says so.
- **Two services given the same log path overwrite each other's log.** Each start truncates the file it is given, so every service needs its own.
- **A service log has no size cap.** A service that prints without end grows its log without limit. Only the last 2000 bytes go into an error.
- **The child's process group is stopped just after the child is reaped.** Once the child is gone and its group is empty, the group id is free, so in theory a reused id could be hit. For `run_child` the window was measured at a median of 35 microseconds and a maximum of about 120, over 60 runs with spies and other work running. It needs a process id wrap to land in it. A group that still has a member keeps its id. The service runner has the same window, and it is longer when the service ended by itself, because the leader is reaped before the first signal: a median of 10 microseconds after a normal stop, where SIGTERM goes first, about 50 (up to about 140) when the service died while the body used it, and about 500 (up to about 900) when it exited during start, because the log is read in between.
- **A child's output is kept on disk while it runs, and a process that outlives the child can keep writing to it.** ARDE keeps the last 1 MB of a check's output and refuses a `goinspect` reply over 64 MB. A command that writes directly, such as an extra test command, still uses as much disk as it writes until it ends, and a process that started its own session can go on writing to the deleted file after ARDE has returned, where `du` cannot see it. `go test ./...` is different: `go` holds each package's output in memory until the package ends, so a test that prints without end costs memory there before it costs disk. Processes in the child's own group are killed when it exits.
- **No sandbox for untrusted merge-request code.** A separate sandbox is a non-goal for now.
- **Child output in a message is short and shows no control character.** An error keeps the last 2,000 bytes of what a child printed. In those bytes and in `CheckResult.output`, each control character except a line break and a tab is written out as `\xNN`, so a test cannot rewrite the terminal's title or clear the screen. `CheckResult.output` is not cut to 2,000 bytes: it keeps up to 1 MB per stream, because the repair loop reads it. A test can still print text that looks like ARDE's own section header, such as `== test (exit 0) ==`, so that text is data and code decides pass or fail from the booleans alone.

## Prompt injection and data

- **Repo text can steer the agents.** Comments, READMEs and test names reach the models as plain input. A poisoned comment can steer a fact or a sentence in the docs. Code limits what that can reach: an agent has no shell or write tools, and it cannot set a command to run. A rule with no HTTP effect still goes unchecked, so a false one can reach the docs. This is reasoned: no agent has run against a hostile repo.
- **What the agents read leaves the machine.** Whatever an agent reads goes to Anthropic, including any secret committed to the target repo, and it is also stored in `debug.log`. Run folders can be read by their owner alone.
- **A native run has no container.** With `uv run arde`, repo code runs as the developer, with access to the home directory and the credentials in it.
- **Redaction is exact match.** The tracer replaces the API key wherever it appears whole. A key that was encoded or split on the way in would pass through. Only `trace.jsonl` and `debug.log` go through the tracer: `report.json`, `service.log` and stderr do not.

## What it understands

- **Go `net/http` only.** Other frameworks and other languages are not supported. Go idioms sit behind one interface so a second language can be added.
- **Names in facts are ASCII and plain.** A struct, field, type or error code with a non-ASCII letter, a generic type such as `Page[Product]`, or a `map` or `interface{}` response type fails validation instead of being written into a comment or tag. A service that uses them cannot be documented until the shape is allowed in the domain models.
- **`extract_inventory` needs a repo that compiles.** `goinspect routes` reads the service through the type checker, and it cannot read a package that does not build. The pipeline's baseline checks prove the build first.
- **The inventory covers the service built from `main_package`, by import.** Only `main_package` and the packages of its module that it imports, directly or not, count. A route, param, env var, error or response field from any other folder of the repo is left out and listed in `dropped`, such as `cmd/admin/main.go:13: route outside main_package ./cmd/api`. A plain struct or function there is left out with no line, because nothing about it was lost. `main_package` must name a folder here: `./main.go` passes the type and then stops with a message.
- **A path must be one the compiler knows.** A string literal, a const and a sum of consts are read. Anything else stops the run with exit 3, so a loop over a table of routes stops it. A site inside a function that a route pattern matches is the one exception, because the pattern reads the path at that function's calls. A function a pattern matches at one call counts at every static call to it, whatever the receiver is called, so a pattern cannot lose a route by naming too little.
- **A registration is found when the compiler can name its target.** Every static call to `net/http.Handle`, `net/http.HandleFunc`, `(*net/http.ServeMux).Handle` or `.HandleFunc` is a site, in any package the service imports. Two forms are not seen, and a route in either is lost with no message: a call through an interface, and a method value held in a variable, such as `add := mux.HandleFunc`. A route pattern on the call adds either one. A route that another module adds is not listed either, such as one registered in the `init` of a dependency, and `_ "net/http/pprof"` is the usual case: only the service's own module is read. A function held in a variable that wraps a registration cannot be a wrapper, because no pattern reaches a variable's body, so its site stops the run.
- **A route on a mux nothing serves is still listed.** Reading source cannot show which mux reaches `ListenAndServe`, so `http.HandleFunc` in a service that serves its own mux gives a route that answers 404, as does a second mux that is never served. This was measured on a fixture. The planned live check in Task 12 owns finding such a route.
- **Paths that something else changes are not resolved.** Every call to `http.StripPrefix` in the service stops the run with exit 3, naming the place, whether it sits at the site, behind an import name, in a variable or in a helper. A site inside a wrapper stops it too when its path holds a constant with a slash, such as `"/v1"+path`, because the path at the wrapper's calls is missing what the wrapper adds. A wrapper that adds a prefix held in a variable or a field is not seen, so its paths read short. Router groups in another framework are not seen either: in a Gin-style sample the matcher reported `/ping` for `/v1/ping`. A live check should get a 404 and stop the run, but that is untested.
- **A handler of type `*http.ServeMux` is a mount, not a route, and so is one behind middleware.** The routes on the mounted mux are listed with the paths they are registered under, which are the whole paths when nothing strips them. A mux returned as a plain `http.Handler` has that type at the site, so its mount reads as an `ANY` route beside the real ones.
- **The call graph is static.** It misses calls through interfaces and through function values it cannot name, such as one read from a struct field or a map. A closure is followed, because a reached function's closures count as reached. Stored requests are the backstop.
- **A fingerprint covers function bodies, not package state.** A package-level `var` or type, and a function that runs only to fill a `var` or inside `init()`, are outside it. `declarations` reports such a change but cannot say which routes it touches.
- **A fingerprint sees one build.** A file excluded by build constraints on the machine running it is not hashed, so an edit behind a custom tag, or in `helper_linux.go` on a Mac, moves nothing.
- **Only Go source in the module is hashed.** Assembly bodies, files read through `//go:embed` and code in other modules, vendored ones included, are outside it.
- **Code of another module under the same path has no body to hash.** That is a nested module, a module that a `replace` points at, a plain dependency under the same path prefix, and a `go.work` member. A route that reaches one gets no fingerprint, with the reason `no body`, and counts as changed on every run. A `testdata/` or `_`-prefixed folder of the module itself is loaded and hashed when the service imports it.
- **A package const used only as an array length inside a type declared in a function is not in that function's fingerprint.** SSA prints the type by name, and the syntax holds only the const's name. `declarations` still reports the const.
- **Adding `oneOf` or `binding:"optional"` to an anonymous struct moves a fingerprint**, because the SSA listing prints the type with its tags. This only over-reports, and ARDE writes those tags on named structs.
- **A new instantiation of a generic handler moves that handler's fingerprint.** The walk starts from every instance of a generic root, so a new type argument adds code to it. This only over-reports.
- **Any edit to a cgo file can move a route that calls C**, even a comment, because cgo names its symbols from a hash of the file. This only over-reports.
- **`goinspect` does not print an expression that spans more than 1,024 bytes of source.** An argument, a struct field's type or tag, or a callee past that size reads `(too long to print)`, or `(too long to print).Get` for a chain, so a pattern on the end of a chain still finds the call. A handler written in place past that size is `(inline)` as before, and a string literal keeps its value. Printing nested calls costs the square of the file's size, so a small file could ask for gigabytes. What is left is linear in the source, with a high constant: about 170 times its size for a file made only of nested calls under the cap, so a very large hostile file still costs memory until the 120 s timeout or the 64 MB reply limit stops it. Hashing streams, so its memory does not grow with the dump. It still takes time proportional to nodes times depth, and the timeout stops that too.
- **Patterns match the callee as text.** An unanchored regex can match text inside a chained call, so anchor them.
- **`main_package` must be `.` or start with `./`.** Any other text could name a package outside the repo, such as `cmd/go` in the toolchain or a dependency's program. So a service whose `main` lives in another module cannot be named: Go also refuses a nested module named by `./path`. `./...` passes the type and stops at the check that a service is one package `main`.
- **Hand-edited `@` lines are overwritten** from the wiki on the next run.
- **`@version` renders as `0.0.0`**, because the repo has no source for it and ARDE will not invent one.
- **The comment-only rule is Go-only.**
- **The comment-only rule is an allow-list, so it answers "real" for much that is harmless.** Only ordinary comment lines (a whole line starting `// `, no directive form, no `/*` or `*/`) and the tags `oneOf` and `binding:"optional"` may differ. An edited block comment, an edited trailing comment, an added blank line, a doc comment written with `///`, any directive, a line holding `+build` or `Code generated`, a byte order mark on one side only, and a file over 8 MiB, which is never read, all count as real, and so does any comment edit in a file with `"C"` or `` `C` `` text, or in a `_test.go` file that holds the word `Example`. A list of dangerous forms could never be complete, and a wrong "real" costs a fraction of a cent while a wrong "comment-only" ignores a change.
- **A comment-only edit can still change a program that reads its own source or its own line numbers.** A file named by `//go:embed x.go` or `//go:embed *.go` is data to the program, and a comment added above `runtime.Caller(0)` moves the line it reports. No rule that looks at one file can see this.
- **An allowed tag is part of a type's identity.** `oneOf` or `binding:"optional"` on a named struct can stop an assignment to an unnamed struct, or a `~struct` constraint, from compiling, and `reflect` can read the tag back. ARDE's own tag edits go through the build check, and a hand edit of this kind reads as comment-only.
- **Embedded struct fields are not response fields.** Their fields are promoted into the parent's JSON object, and the inventory cannot say so. An embedded field with a `json` name is also left out, although Go treats it as a named field. Two structs with one name in different packages are both listed and told apart by their file, but a fact that names a struct by its name alone cannot say which one it means. Task 13 decides how a fact picks between them.
- **The inventory includes files for other platforms and behind other tags.** `declarations` and `match` skip `vendor`, `testdata`, names that start with `_` or `.`, a folder with its own `go.mod`, and a file whose build constraint requires the tag `ignore`: the tag alone, or an `&&` with it, in `//go:build` or in any `// +build` line. Every other file stays in, because some build includes it. That covers a file for another OS, one behind a tag such as `e2e`, and one behind a negated tag such as `!windows`. A route is the exception, because the type checker reads this machine's build alone and the service built here has no such route: a route pattern that matches in `only_windows.go` gives a line in `dropped`, not a route, and a registration no pattern matches there is not seen. `ignored_files` lists the files this machine's build leaves out, whether they are tests, tool files such as `tool.go` or files for another platform such as `p_windows.go`.
- **A link to a regular file counts as the file it builds as.** The Go tool compiles a link named `x.go` that leads to a regular file, so `declarations`, `match` and `compare` read it too, under the link's own name, and an edit to its target moves the link's declarations. A link to anything else is skipped: a folder, as `./...` skips it, a broken link, which stops the Go tool itself, and a FIFO. A link that leaves the repo never gets this far, because the gate refuses the repo first.
- **Params, env vars and error codes are read from literals.** A route pattern with a host, such as `GET example.com/x`, stops the run. A param name, env name or error code that is not a string literal is dropped, a const included, so a repo that wraps `os.Getenv` in its own helper gets nothing from the default pattern, and Discovery has to supply one for that helper. Each dropped call is listed in the inventory's `dropped`, with its file and line. The call inside a helper that a pattern of the same kind matches is not listed, because that pattern reads the value at the helper's calls. A pattern that matched no call is named in `unmatched_patterns`. Neither shows a call that no pattern matched, so `dropped` is not a full account of what was missed.
- **Repo text in the inventory is one line, with a capped length.** A handler, param, env var, struct, field, JSON key or make target holds at most 200 characters, a declared type 500, a route path 1,000 and a file name 1,024, and none may hold a line break or a control character. A function id holds at most 1,000 characters and a declaration id 1,234. A route that fails this stops the run with exit 3. A param, env var, error code, response field, make target or declaration id that fails it is left out and listed in `dropped`, without its text. An error code must also be a name a fact can carry, so the message in `http.Error(w, "not found", 404)` is no code and goes to `dropped`. A status keeps its first 80 characters on one line. A file name in a dropped line or an error is printed with its control characters escaped. The number of items is not capped, so a large repo gives a large inventory.
- **A struct declared inside a function, and an anonymous struct, are not response fields.** `declarations` reads top-level types only.
- **A `json:"n,string"` field keeps its declared type.** The inventory says `int` for a field whose reply carries a string.
- **`GET /{$}` and `GET /` are one route key.** ARDE writes the exact-root pattern `/{$}` as `/`, so the two read as one route. `route_fingerprints` gives such a key no hash when its functions differ, with the reason `shared key`, and the route counts as changed on every run.
- **A fingerprint starts from a function the compiler can name.** A name, a method value, a conversion such as `http.HandlerFunc(x)`, middleware around one handler and a factory such as `s.handleX()` all lead to one exact function. A function written in place is `(inline)`, with no function id, and has no declaration to carry a comment. A local variable, a field, a package variable, a table entry, a method of an interface and a function from another module have no id either, and neither does a call that takes several handlers, because a root at one would miss edits to the rest. Each such route has no hash, with the reason `inline` or `no function`, and counts as changed on every run.
- **Middleware is outside the fingerprint of the handler it wraps.** The root is the handler, so an edit to the middleware moves no route, and `declarations` reports it.
- **A Makefile that cannot be read stops the run.** Exit 2, for a file that is unreadable or over 1 MiB, because ARDE reads it itself with no timeout.
- **Make targets come from a regex over the top-level Makefile.** A target that an included file defines, or that a variable builds, is missed.
- **Extra test commands run without a shell.** They are split into words, so `&&`, pipes and redirects do not work in them.
- **No detection of critical changes** that alter a project's scope or can damage a service while the tests still pass.
- **No stored knowledge graph.** It was dropped. Only cross-repo questions such as "which services use this contract?" would reopen it.

## Workspaces

- A fork has a different URL, so it gets a new workspace and a full first run.
- A second branch in the same workspace counts as a change from the last successful run.
- The wiki is not exported into the target repo. A later `--export-wiki` flag could write a readable one-way copy.

## The judge

- It cannot test rules that have no HTTP effect.
- An arithmetic slip looks like a mismatch, and a lucky guess passes.
- An error code is exempt as unreachable only if the wiki holds an `unreachable` fact with code evidence. A wrong claim of unreachable is a known limit.
- It has not been run yet, so its catch rate is unknown.

## Cost

- **The cap can be overshot by one call.** A call's price is known only after it is paid for. The run stops once spending reaches the cap, but the last call can pass it by its own cost: at the shipped settings the worst single Opus 5.5 call costs $4.32, from 1M uncached input tokens and 16,000 output tokens.
- **A stream that breaks is charged only for what it had reported.** The first event says what the prompt used, so those tokens reach the trace and the cap. Output tokens arrive in the last event, so those written before the break are missing and the total reads low. A failure before the first event has nothing to charge. That the real API's first event carries the prompt's tokens comes from the SDK's types and has not been seen live, and that such a call is billed is assumed, not measured against a bill.

## The model API

Measured against the live API on 2026-11-02, with Opus 5.5.

- **Every request streams.** The SDK refuses a call that does not stream above about 21,333 `max_tokens`, and thinking counts against that limit. A dropped stream is not retried, because the SDK retries only before a stream starts, so it ends the run with a next action. See [decision 0011](decisions/0011-stream-every-request.md).

- **Strict tool use is refused for the repo profile and for the facts.** The API answers `For 'object' type, 'additionalProperties: object' is not supported` for the open `args` dict in the profile, and `Schema type 'oneOf' is not supported` for the fact union. Rewriting `oneOf` as `anyOf` did not help on Haiku 5.5: the API then said the compiled grammar was too large. Tools with these schemas must be sent with `strict=False`, and code validation holds the guarantee.
- **A refusal ends the agent, with no retry on another model.** The server-side fallback needs the beta client, and Haiku 5.5, which the classifier uses, has no fallback at all. The agent stops with the reason `refused`. The category and explanation go to `model_call` and `debug.log`, and `AgentStopped` exposes the category, so false positives can be counted on the first real run. No live refusal has been seen yet, so this rests on the SDK's types.
- **An error result with no text is refused by the API** (HTTP 400). The agent loop sends a stand-in text, so a tool that fails silently does not end the run.

## Not tested yet

As of Phase 0. Move an item out of this list when a test or a measurement covers it.

- Linux, Windows and amd64 hosts. The container was tried only on Docker for Mac (arm64).
- Agents producing patterns or facts. The API client itself has been run live, but no agent has produced these yet.
- A full run end to end, and any second repo. No-config onboarding is a claim, not a result.
- Run cost. The estimate of about $3 per first run with prompt caching rests on a review, not a measurement.

## Known costs

- The container image is about 980 MB, because it holds both the Go and Python toolchains.
- `swag` v2.0.0-rc6 is a pre-release. It is pinned, and the run's checks would surface a bad spec.
