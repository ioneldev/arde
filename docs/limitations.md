# Limitations

What ARDE does not do, and what has not been tested. Most of it comes from the [design](superpowers/specs/2026-11-01-arde-design.md). The writable-mount risk was found later, in a security review of the container experiment. Add to this page when you find a new limit.

## Trust and containers

- **Repos must be trusted.** The repo's code runs in the same container as ARDE and the API key. Removing `ANTHROPIC_*` from child processes limits accidents, but it is not a security boundary: code running as the same user can still read the parent's environment. The security review measured this on macOS: a child with the allow-listed environment read a stand-in value from the parent's starting environment through `KERN_PROCARGS2`, and a value the parent set after it started did not show. Measured again on Linux, in the container: the child read the stand-in from `/proc/<parent>/environ`, and from `/proc/1/environ` too, because the init process gets `.env` as well, and a value set after the start did not show.
- **The local repo is mounted read-only.** ARDE copies a local repo into its workspace and never writes to it, so `compose.yaml` mounts `REPO_PATH` at `/repo` read-only, and repo code in the container cannot change the host's copy, for example by planting a git hook that later runs on the host. Measured: even root in the container gets `Read-only file system` there. On a Linux host the mount keeps the host's owner, which can differ from `ARDE_UID`, and git refuses a repo that another user owns, so the image lists `/repo` and `/repo/.git` in git's system `safe.directory`. That check guards against running the settings of a repo someone else owns, and ARDE already treats a local repo's settings as untrusted. Measured with a volume owned by another user standing in for the Linux host, because Docker Desktop shows a mount as owned by whoever reads it.
- **What the container keeps from the repo's code, and what it does not.** It keeps the host: the repo's build, tests and service see no host home folder, no host file but the repo, mounted read-only, and no host credential, such as SSH keys, cloud logins or your own git settings. It does not keep the API key from them. No child gets an `ANTHROPIC_` variable, but every child runs as ARDE's own user, so it can read the key from `/proc/<ARDE's pid>/environ`, or from `/proc/1/environ`, because the init process gets `.env` too. `tests/test_container.py` keeps this in sight: a repo's test there reads the key from `/proc/1/environ`. Nor does it keep the volume from them, as the next line says. The fix is to run the repo's code as another user than ARDE.
- **The `/data` volume is shared across repos, and each repo's Go caches are in its own workspace.** The volume holds every repo's workspace. A repo's Go commands, `goinspect` and swag included, get `GOCACHE`, `GOPATH` and `GOMODCACHE` in `cache/` of that repo's workspace, so a run reads only what its own repo's runs wrote, and no cache is shared by every repo (tested). That holds natively too, so the first run on a repo compiles the standard library and fetches the repo's modules again, once. It is no wall against a hostile repo: its code runs as ARDE's user and can write into any workspace in the volume, another repo's caches and its `profile.override.yaml`, the file `extra_test_commands` trusts, included. This is reasoned, not tested. Give a repo you trust less a volume of its own: `docker compose run --rm -v arde-<name>:/data arde --repo ...` replaces the shared one for that run (measured). The home folder is outside the volume: `HOME` is `/home/arde`, new in every container, and `GOENV` is `off`, so neither `~/.gitconfig` nor the `go env` file carries from one run to the next. Measured: with `HOME` in the volume, a `~/.gitconfig` that an earlier container left redirected the next run's clone through `url.<base>.insteadOf`.
- **Go commands read three settings from the user's `go env` file, and nothing else in it.** ARDE sets `GOENV=off` for every Go command, because that file lives under `HOME` and can hold a `GOFLAGS` with `-toolexec`. Once per process, in the parent, it asks `go env` for `GOPRIVATE`, `GONOPROXY` and `GONOSUMDB`, with the exported values of those three and the user's `XDG_CONFIG_HOME` and `GOENV` so that it looks where the user's own `go` looks, and it passes the answer on as Go gave it. Go decides which value wins and derives `GONOPROXY` and `GONOSUMDB` from `GOPRIVATE`, so a private repo builds and its module paths stay off the public proxy and checksum database. A `GOPROXY`, `GOSUMDB` or `GOTOOLCHAIN` that only the file holds is ignored on purpose, so a poisoned file cannot redirect where modules come from or switch the toolchain: every command runs with `GOENV=off`, and the probe itself runs with `GOTOOLCHAIN=local`, so neither the file nor a `go.mod` above the temporary folder can make it start or download another toolchain. Export anything else you need. An empty exported value counts as not exported. Those three settings can weaken checksum checks for the paths they name, which is why repos must be trusted. If `go env` fails or leaves one of them out, the run stops, because going on without them would send private paths to the public proxy. In the container `GOENV` is `off`, so the probe reads no file either, and those three come from `.env` alone.
- **A link that leads out of a repo stops the run.** Every `GoAdapter` method that takes a repo first walks all of it, `.git` included, and refuses any link whose real path is outside the repo's real path, with exit 2. The message names the link and never its target. This holds for every file, because the Go tool follows links and quotes a `go.mod` it cannot parse, and a repo's `go.work` can name a module inside `.git`. So a hook linked to a shared folder stops the run too, and the next action is to replace the link with the file. A hard link looks like a file, so it passes. A clone from a URL makes none, and a clone from a local path hard-links only the files in `.git/objects`, which Go does not read. A name the walk can list but not inspect, such as one in a folder that can be read but not entered, stops the run as a folder it cannot list does. The walk runs once per call, when the method starts, so a link planted after it is not seen until the next call. A test can plant one while `go test` runs, and a later Go command in the same `run_checks` call, such as `go test -list` or `go list`, then quotes the file the link points to: the boundary review measured a passing test that linked `leak.go` to a file outside, and the error quoted that file's first line. A process the repo left running, such as a test's child or the service Explore runs, can do the same between a later call's walk and its Go commands. Either is repo code, which could read the file itself.
- **A repo cannot choose its toolchain unless you let it.** Every Go command runs with `GOTOOLCHAIN=local` unless you export another value, so a `go` or `toolchain` line in `go.mod` can neither start a program found on `PATH` nor ask for a download. The cost is that a repo that needs a newer Go than the one installed stops with Go's own error, such as `go.mod requires go >= 1.99.0`, and `goinspect` itself needs the Go version in its own `go.mod`. Export `GOTOOLCHAIN=auto` to accept the switch.
- **A relative `PATH` entry is removed from every child's environment.** A child changes folder before it looks for a program, so `.` or an empty entry would find a `go` the repo planted. When nothing absolute is left, `PATH` is left out and the system's default path applies, because an empty `PATH` reads as the current folder.
- **A repo decides its own workspace, and nothing above it can.** Every Go command and `goinspect` run with `GOWORK` set to the repo's own `go.work` when that regular file exists, and to `off` otherwise. Without this, Go looks in every folder above the repo, and a `go.work` planted there chose the code that was built and run. An exported `GOWORK` is ignored.
- **A timeout cannot reach a grandchild that started its own session.** The child and its process group are killed, and ARDE stops waiting. A daemon that a test or an extra command started on its own keeps running.
- **If ARDE itself is killed with SIGKILL, a running service is left behind.** The service runner stops the service in a `finally` block, which covers a normal exit, an error and Ctrl-C, and the cli turns SIGTERM and SIGHUP into Ctrl-C (`signals_as_interrupts` in `src/arde/cli.py`), so those two run it too. SIGKILL gives no code a chance to run, and that will stay so. A process that uses the runner without the cli has no handler for SIGTERM or SIGHUP, because Python has none by default, so no `finally` runs there. The service keeps its port and its process group until someone stops it. To find it, look in `ps` for a binary in a folder named `arde-service-` under the temporary directory, and kill its process group. In the container, `docker stop` sends SIGTERM through the init process that `compose.yaml` turns on, and ARDE stops its service and exits 130 well inside Docker's 10 s grace (measured). A SIGKILL, from `docker kill` or at the end of the grace, ends the container and everything in it, the service included.
- **The service gets the grace period only through its leader.** The runner sends SIGTERM to the whole process group, waits up to 5 s for the first process to exit, and then kills the group. A worker that needs longer than its parent to shut down is cut off the moment the parent exits. A service that starts its own session is out of reach of the group, as for any child.
- **A free port is found by binding and closing, so another process can take it before the service binds.** The window is short. A service that loses the race normally exits at once and is reported with its log. If the other process opens the port and answers, the first probe connects to it and the body starts against the wrong process. The service, which could not bind, exits, and the runner reports that as a `ServiceDiedError` with its log when the body ends.
- **A Ctrl-C that lands inside or just after the `Popen` call leaves the service running.** The process exists before `Popen` returns its handle, so the runner has nothing to stop yet, and moving the `try` cannot close that. The window is the 6 ms or so the call takes, plus a median of 77 microseconds, at most 118, from its return to the `try`. A second Ctrl-C between entering the stop and its first signal does the same, in a median of 27 microseconds and at most 41, because the code that notes whether the service had already exited sits outside the stop's `try`. An interrupt raised at each of those points left the service running, measured on macOS at a load average of about 9 on 12 cores, and not on Linux. An interrupt anywhere else in the start, the wait, the body or the stop leaves nothing running.
- **The runner connects to `127.0.0.1` only.** A service that listens on `::1` alone is not found, and fails with the timeout error, which says so.
- **Two services given the same log path overwrite each other's log.** Each start truncates the file it is given, so every service needs its own.
- **A service log has no size cap.** A service that prints without end grows its log without limit. Only the last 2000 bytes go into an error.
- **The child's process group is signalled just after the child is reaped.** Once the child is gone and its group is empty, the group id is free, so in theory a reused id could be hit. It needs a process id wrap to land in the window, and a group that still has a member keeps its id. Measured on macOS over 60 runs of each case with spies, at a load average of about 9 on 12 cores, from the reap to the last signal: for `run_child`, which sends one signal after a child exits, a median of 39 microseconds and at most 411. The service runner sends more: two after a normal stop, the last at a median of 50 and at most 81, and three when the service died while the body used it, the last at a median of 184 and at most 596, because the leader is reaped before the first signal. When it exited during start the log is read in between, so the last of its signals comes at a median of 624 microseconds and at most 829 after the reap. Not measured on Linux.
- **A child's output is kept on disk while it runs, and a process that outlives the child can keep writing to it.** ARDE keeps the last 1 MB of a check's output, stops the run when the event stream of `go test -json` passes 64 MB, and refuses a `goinspect` reply over 64 MB. That stream holds every line a test prints, also from tests that pass, so a repo whose tests print tens of megabytes stops there, where plain `go test` would pass, with the end of the stream in the message. It is read into memory to be counted: a stream of 53.5 MB peaked at 359 MB, measured once on a fixture. A command that writes directly, such as an extra test command, still uses as much disk as it writes until it ends, and a process that started its own session can go on writing to the deleted file after ARDE has returned, where `du` cannot see it. `go test` is different: `go` holds each package's output in memory until the package ends, so a test that prints without end costs memory there before it costs disk. Processes in the child's own group are killed when it exits.
- **A stopped service's port gets up to 5 s to close.** After the kill, the runner waits for the port to refuse connections before it reports that something holds it. Measured on Linux, in the container: a service whose group held a few hundred processes kept its port for up to 2.6 s while the kernel ended them, though none outlived the kill, so a 1 s wait raised a false stop error. On macOS fork is slower, so the same service held about 30 processes and closed its port within 0.15 s.
- **Every child shares the container's 4 GiB memory limit, with no swap.** A build, a test or a service that passes it is killed by the kernel, and ARDE reports the step that failed. Measured: a compiler holding six constants of 1 GiB each was killed, and ARDE stopped with exit 1 and `compile: signal: killed` in the message, which says nothing of memory. A run on a larger repo may need a higher `mem_limit` in `compose.yaml`. `goinspect` is held to the same limit, which is reasoned, not tested. A native run has no limit.
- **A proxy or a private certificate authority does not reach git or Go.** `HTTPS_PROXY`, `HTTP_PROXY`, `NO_PROXY` and `SSL_CERT_FILE` are not in the children's allow-list, so behind a proxy a clone or a module download fails. This is reasoned from `src/arde/adapters/child_env.py`, not tested.
- **No sandbox for untrusted merge-request code.** A separate sandbox is a non-goal for now.
- **Child output in a message is short and shows no control character.** An error keeps the last 2,000 bytes of what a child printed. In those bytes and in `CheckResult.output`, each character of the Unicode categories Cc, Cf, Zl and Zp except a line break and a tab is written out, as `\xNN` up to U+00FF, `\uNNNN` up to U+FFFF and `\UNNNNNNNN` past it, so a test cannot rewrite the terminal's title, clear the screen, break a line, or hide or reorder the text a reader sees. That covers the direction controls and marks, U+061C, U+200E, U+200F, U+202A to U+202E and U+2066 to U+2069, the zero-width characters, U+200B to U+200D, the soft hyphen and the tag characters. `src/arde/domain/base.py` holds the one list, and a test checks it against Python's Unicode database. Text from a repo shown in an error, such as a route's path, is made one line with each of these characters a space. An emoji joined with U+200D therefore shows as its parts. `CheckResult.output` is not cut to 2,000 bytes: it keeps up to 1 MB per stream, because the repair loop reads it. For the tests that stream is readable text rebuilt from the events, without what a passing test printed, as plain `go test` leaves it out. A test can still print text that looks like ARDE's own section header, such as `== test (exit 0) ==`, so that text is data and code decides pass or fail from the booleans alone.

## Prompt injection and data

- **Repo text can steer the agents.** Comments, READMEs and test names reach the models as plain input. A poisoned comment can steer a fact or a sentence in the docs. Code limits what that can reach: an agent has no shell or write tools, and it cannot set a command to run. A rule with no HTTP effect still goes unchecked, so a false one can reach the docs. This is reasoned. Scripted runs on `tests/fixtures/hostile` show a planted route and planted-only evidence refused, but the test that runs the real models on that fixture is opt-in (`make eval`), so `make check` does not cover it.
- **What the agents read leaves the machine.** Whatever an agent reads goes to Anthropic, including any secret committed to the target repo, and it is also stored in `debug.log`. Run folders can be read by their owner alone.
- **An agent sees the first 200,000 bytes of a file.** `read_file` stops at the last whole line inside that limit and says so, and `grep` searches the same part, so text past it can be neither found nor read. A file with a NUL byte counts as binary: `read_file` refuses it and `grep` passes over it. Text that is not UTF-8 shows U+FFFD in place of each bad byte. `list_files` shows at most 1,000 paths and `grep` at most 100 lines, each cut at 500 characters, and both say how many there were.
- **An agent tool checks a path when it is called.** Each call resolves the path, links included, and refuses one that leads out of the repo, so a link planted after the run started is caught at the next call. A process the repo left running, such as the service Explore probes, could still swap a folder for a link between that check and the read. That is repo code, which could read the file itself.
- **A probe sends GET or HEAD, gets 10 s for the whole reply, and records a body of up to 1 MiB.** The 10 s cover the connection, the status line, the headers and the body, and every read waits only for what is left of them, so a service that sends a byte at a time cannot hold a probe longer. A reply that is late or too large is refused, not cut, and nothing is recorded for it. The model sees the first 20,000 characters of a body, which is read as UTF-8 whatever charset the reply names. Only the `Content-Type`, `Allow` and `Location` headers reach the model, and only the status, the content type and the body are recorded.
- **A native run has no container.** With `uv run arde`, repo code runs as the developer, with access to the home directory and the credentials in it.
- **Redaction is exact match.** The tracer replaces the API key wherever it appears whole. A key that was encoded or split on the way in would pass through. Only `trace.jsonl`, `debug.log`, `report.json` and the summary the cli prints for a run that started go through the tracer's redaction. The service logs, `service-*.log`, and anything else on stderr, such as a Python traceback, do not.

## What it understands

- **Go `net/http` only.** Other frameworks and other languages are not supported. Go idioms sit behind one interface so a second language can be added.
- **Names in facts are ASCII and plain.** A struct, field, type or error code with a non-ASCII letter, a generic type such as `Page[Product]`, or a `map` or `interface{}` response type fails validation instead of being written into a comment or tag. A service that uses them cannot be documented until the shape is allowed in the domain models. The run lists each such inventory name in its warnings, and the docs leave it out.
- **`extract_inventory` needs a repo that compiles.** `goinspect routes` reads the service through the type checker, and it cannot read a package that does not build. The pipeline's baseline checks prove the build first.
- **The inventory covers the service built from `main_package`, by import.** Only `main_package` and the packages of its module that it imports, directly or not, count. A param, env var, error or response field from any other folder of the repo is left out and listed in `dropped`. A route from there is listed in `dropped` only when a route pattern matched it, such as `cmd/admin/main.go:13: route outside main_package ./cmd/api`: a registration of `net/http` that no pattern names is found through the type checker, which reads this service alone, so it leaves no line. A plain struct or function there is left out with no line, because nothing about it was lost. `main_package` must name a folder here: `./main.go` passes the type and then stops with a message.
- **A path must be one the compiler knows.** A string literal, a const and a sum of consts are read. Anything else stops the run with exit 3, so a loop over a table of routes stops it. A site inside a function that a route pattern matches is the one exception, because the pattern reads the path at that function's calls. A function a pattern matches at one call counts at every static call to it, whatever the receiver is called, so a pattern cannot lose a route by naming too little.
- **A function that registers routes for its callers is read in three forms, and any other stops the run.** A route pattern that matches such a function is read at its calls, and a site inside it whose path is not a constant must build that path from the function's parameters in one of three ways: the path parameter alone, a constant method and a space before it, as in `"GET "+path`, or the method parameter, a space and the path parameter, as in `method+" "+path`, with the method's position given as `method` in the pattern's args. A method parameter of a named string type may be converted at the site, as in `string(m)+" "+path`. Each call then registers the path built the same way from its own constants, so the constant method wins over the function's name, and the method at a call must be a constant and not empty: an empty one stops the run with exit 3 and a message that says the method is empty, here and at a call to another module's router whose pattern names a `method`. Anything else stops the run with exit 3 and names the site: a prefix such as `"/v1"+path`, a suffix, a local variable, `path.Join`, or a call that hands the path to another such function. The function must also never write its path or method parameter, because the parameter is still the same variable after a write: an assignment, `+=`, a short declaration that declares it again, a range that assigns it, or its address taken, anywhere in the function or a closure in it, stops the run and names the place of the write too. So a prefix held in a field stops the run in every form, whether it is added at the site, as in `"GET "+g.prefix+path`, or first, as in `path = g.prefix + path`. So does a call to such a function that registers no route there, because its handler is a mux or the function registers no path it is given. A function with two sites gives two routes at each call. In the first form the method comes from the path the call passes, as in `"GET /x"`, or else from the function's name, such as `get`, which `net/http` itself does not enforce.
- **A registration is found when the compiler can name its target.** Every static call to `net/http.Handle`, `net/http.HandleFunc`, `(*net/http.ServeMux).Handle` or `.HandleFunc` is a site, in any package the service imports. Any other use of one of them, or of a function that a route pattern matches as one that registers routes for its callers, stops the run with exit 3 and names the use, because a call ARDE cannot see is a route it cannot list: a method value or a function value, such as `add := mux.HandleFunc` or `registerShop(a.get)`, an assignment, a store into a field or a slice, and a method expression such as `(*app).get`. So does a call or a method value through an interface that such a function's type satisfies, its own or one that gets the method by embedding, whether or not a pattern matches the call, because a pattern reads that call with the method from its name and not the form the function registers. Its stop names the method called, the interface and each type behind it, such as `*http.ServeMux` behind a `Router` interface, so you can tell which registration to make a direct call. An anonymous struct that embeds such a function's type and satisfies the interface is not looked at. A route that another module adds is not listed either, such as one registered in the `init` of a dependency, and `_ "net/http/pprof"` is the usual case: only the service's own module is read. A function held in a variable that wraps a registration cannot be a wrapper, because no pattern reaches a variable's body, so its site stops the run.
- **A route on a mux nothing serves is still listed.** Reading source cannot show which mux reaches `ListenAndServe`, so `http.HandleFunc` in a service that serves its own mux gives a route that answers 404, as does a second mux that is never served. This was measured on a fixture. `validate_profile` flags such a route when the service answers it as it answers a path that cannot exist, but only for a saved profile (see Discovery and the profile).
- **A table or a switch behind one handler is not seen.** ARDE reads registrations, so what a handler does with a request is outside the inventory. Measured on a fixture: a handler that looks `r.URL.Path` up in a table of pages gives one `ANY /` route and no line in `dropped`, and a `ServeHTTP` that switches on `r.Method` gives one `ANY` route. A profile cannot express either shape.
- **Paths that something else changes are not resolved.** A call to `http.StripPrefix` in the service stops the run with exit 3, naming the place, whether it sits at the site, behind an import name, in a variable or in a helper. One exception: a direct call to `http.FileServer` or `http.FileServerFS` as its handler, resolved by type, does not stop. No route sits under a file server, so the site reads as a route with no function id, which counts as changed on every run. A variable that holds a file server, middleware or a conversion around one, and a function of the service with the same name all still stop. A function of the service that adds a prefix to the path it is given stops the run, as the line above on such functions says. Router groups in another framework are not seen either: in a Gin-style sample the matcher reported `/ping` for `/v1/ping`. `validate_profile` flags a route that answers like a path that cannot exist.
- **A handler of type `*http.ServeMux` is a mount, not a route, and so is one behind middleware that passes it on.** The routes on the mounted mux are listed with the paths they are registered under, which are the whole paths when nothing strips them. A mux given to a function of the service that does not pass it on, such as `routesPage(mux)`, is a route of that function, and one given to a call the compiler cannot name, such as middleware held in a variable, is a route with no function. Either way the mux's own routes are still listed. A mux behind middleware that is also given a function written in place is still a mount. A mux's `ServeHTTP` taken as a value, as in `root.HandleFunc("/c/", c.ServeHTTP)` or `logged(b.ServeHTTP)`, counts as the mux, and middleware that serves through its handler parameter's `ServeHTTP` value, as `http.HandlerFunc(next.ServeHTTP)` does, passes the mux on. A mux handed to a function that a route pattern matches as one that registers routes for its callers is a mount at the call's path when every site of that function registers its handler parameter at its path parameter alone, as it is or behind middleware that passes it on. When the function does more with it, such as registering `"GET "+path` or handing it to a factory that does not serve it, the run stops with exit 3 and says the function mounts a mux. A mux returned as a plain `http.Handler` has that type at the site, so its mount reads as an `ANY` route beside the real ones.
- **The call graph is static.** A call through an interface is followed only to the methods of the service's own types that reached code makes into an interface, on value and pointer receivers and promoted ones too, and of those only the ones an interface can call: every exported method, and an unexported one only when an interface of its own package, an interface literal included, declares its name, because `reflect` cannot call an unexported method and no other package's interface can name one. So an edit to such a method moves the route, and an edit to an unexported method moves only the routes whose code calls it. A value made into an interface by code no route reaches, such as one kept in a package variable of interface type, is missed, and so are function values it cannot name, such as one read from a struct field or a map. A closure is followed, because a reached function's closures count as reached. Stored requests are the backstop.
- **A fingerprint covers function bodies, not package state.** A package-level `var` or type, and a function that runs only to fill a `var` or inside `init()`, are outside it. `declarations` reports such a change but cannot say which routes it touches.
- **`changed_declarations` does not see imports.** An import is no declaration. Measured: swapping `html/template` for `text/template` gives an empty list, and so does adding `_ "net/http/pprof"`, which also leaves the inventory and every fingerprint as they were, though it adds routes to a service that serves the default mux. Only `compare` sees either edit, so a report on one names a file and nothing else.
- **A fingerprint sees one build.** A file excluded by build constraints on the machine running it is not hashed, so an edit behind a custom tag, or in `helper_linux.go` on a Mac, moves nothing.
- **Only Go source in the module is hashed.** Assembly bodies, files read through `//go:embed` and code in other modules, vendored ones included, are outside it.
- **Code of another module under the same path has no body to hash.** That is a nested module, a module that a `replace` points at, a plain dependency under the same path prefix, and a `go.work` member. A route that reaches one gets no fingerprint, with the reason `no body`, and counts as changed on every run. A `testdata/` or `_`-prefixed folder of the module itself is loaded and hashed when the service imports it.
- **A package const used only as an array length inside a type declared in a function is not in that function's fingerprint.** SSA prints the type by name, and the syntax holds only the const's name. `declarations` still reports the const.
- **Adding `oneOf` or `binding:"optional"` to an anonymous struct moves a fingerprint**, because the SSA listing prints the type with its tags. This only over-reports, and ARDE writes those tags on named structs.
- **A new instantiation of a generic handler moves that handler's fingerprint.** The walk starts from every instance of a generic root, so a new type argument adds code to it. This only over-reports.
- **Any edit to a cgo file can move a route that calls C**, even a comment, because cgo names its symbols from a hash of the file. This only over-reports.
- **`goinspect` does not print an expression that spans more than 1,024 bytes of source.** An argument, a struct field's type or tag, or a callee past that size reads `(too long to print)`, or `(too long to print).Get` for a chain, so a pattern on the end of a chain still finds the call. A handler written in place past that size is `(inline)`, and a string literal keeps its value. Printing nested calls costs the square of the file's size, so a small file could ask for gigabytes. What is left is linear in the source, with a high constant: about 170 times its size for a file made only of nested calls under the cap, which is worked out and not measured, so a very large hostile file still costs memory until the 120 s timeout or the 64 MB reply limit stops it. Hashing streams, so its memory does not grow with the dump. It still takes time proportional to nodes times depth, and the timeout stops that too.
- **Patterns match the callee as text.** An unanchored regex can match text inside a chained call, so anchor them.
- **`main_package` must be `.` or start with `./`.** Any other text could name a package outside the repo, such as `cmd/go` in the toolchain or a dependency's program. So a service whose `main` lives in another module cannot be named: Go also refuses a nested module named by `./path`. `./...` passes the type and stops at the check that a service is one package `main`. A path element that starts with a dot is refused, such as `./.git/x` or `./cmd/.hidden`, because the Go tool passes over such a folder.
- **Hand-edited `@` lines are overwritten** from the wiki on the next run. Every comment line whose text starts with `@` in a function's doc comment is taken for an annotation and removed before the render writes, so a person's `// @todo` above a function goes too. A line written `//@Summary`, with no space, is left as it is, and swag still reads it.
- **One function carries one annotation block.** A handler that serves several routes, or several verbs of a route registered with no method, gets one `@Router` line per route, and the fact of the first route, by path and then method, gives the summary, params and responses for all of them.
- **Some shapes stop the render rather than get a wrong annotation.** A field on the same line as its struct has no line of its own for a comment. A tag ARDE must change has to be the first backquoted string on the field's line, with no backslash, no key twice and a space between pairs, and a field with no tag cannot take a `oneOf`. swag's `@Router` reads only GET, PUT, POST, DELETE, OPTIONS, HEAD and PATCH, and paths of ASCII letters, digits and `_ . / - { } ( ) + : $`. A param name holding a parenthesis would read as an attribute. A response type named bare in `@Success` is written as given, so one declared in another package than its handler must be named with its package. A `oneOf` variant named bare is written with its package from the inventory, and a bare name that two packages declare stops the render.
- **Text from facts is changed where swag or the comparison would misread it.** A double quote becomes a single one, and a parenthesis in a param's description gets a space before it, because swag reads an attribute such as `default(1)` anywhere in the line. `/*`, `*/`, `+build`, a leading `#cgo` or `Output:` and `Code generated` are broken with a space or a hyphen, because the comparison would read the line as more than a comment. A param's choices and default may hold no parenthesis or comma, and its description may not be blank, because no escape exists for them. swag also reads `maxinum` and `mininum` after a space as its own misspellings, so a description holding either hides the param's maximum or minimum, and nothing checks for it.
- **A field comment is ARDE's only while the manifest says so.** It carries no mark, so the next render removes it by its text, from the comments above any field of that file, and a person's identical line there goes too. Delete the workspace and the manifest goes with it: comments ARDE wrote then read as a person's and stay, and a changed description is written beside the old one.
- **gofmt can leave an empty comment line.** It puts `//` between a block and directives such as `//nolint:funlen` below it, and keeps that line when a later run deletes the block.
- **`@version` renders as `0.0.0`**, because the repo has no source for it and ARDE will not invent one.
- **The comment-only rule is Go-only.**
- **The comment-only rule is an allow-list, so it answers "real" for much that is harmless.** Only ordinary comment lines (a whole line starting `// `, no directive form, no `/*` or `*/`) and the tags `oneOf` and `binding:"optional"` may differ. An edited block comment, an edited trailing comment, an added blank line, a doc comment written with `///`, any directive, a line holding `+build` or `Code generated`, a byte order mark on one side only, and a file over 8 MiB, which is never read, all count as real, and so does any comment edit in a file with `"C"` or `` `C` `` text, or in a `_test.go` file that holds the word `Example`. A list of dangerous forms could never be complete, and a wrong "real" costs a fraction of a cent while a wrong "comment-only" ignores a change.
- **A comment-only edit can still change a program that reads its own source or its own line numbers.** A file named by `//go:embed x.go` or `//go:embed *.go` is data to the program, and a comment added above `runtime.Caller(0)` moves the line it reports. No rule that looks at one file can see this.
- **An allowed tag is part of a type's identity.** `oneOf` or `binding:"optional"` on a named struct can stop an assignment to an unnamed struct, or a `~struct` constraint, from compiling, and `reflect` can read the tag back. ARDE's own tag edits go through the build check, and a hand edit of this kind reads as comment-only.
- **Embedded struct fields are not response fields.** Their fields are promoted into the parent's JSON object, and the inventory cannot say so, so the API reference leaves them out of the parent's body table, though its example shows them, and lists the embedded struct under "Other reply structs". An embedded field with a `json` name is also left out, although Go treats it as a named field. Two structs with one name in different packages are both listed and told apart by their file and package, but a fact that names a struct by its name alone cannot say which one it means. The renderer then takes the one the fact links to by its declaration, as `web/payloads.go::type Quote`, and stops when no link says which.
- **A struct with no `json` tag is not a response field,** though `encoding/json` writes its exported fields under their own names. A struct counts once one of its fields has a `json` key, and then an exported field with no tag is listed under its own name.
- **The inventory includes files for other platforms and behind other tags.** `declarations` and `match` skip `vendor`, `testdata`, names that start with `_` or `.`, a folder with its own `go.mod`, and a file whose build constraint requires the tag `ignore`: the tag alone, or an `&&` with it, in `//go:build` or in any `// +build` line. Every other file stays in, because some build includes it. That covers a file for another OS, one behind a tag such as `e2e`, and one behind a negated tag such as `!windows`. A route is the exception, because the type checker reads this machine's build alone and the service built here has no such route: a route pattern that matches in `only_windows.go` gives a line in `dropped`, not a route, and a registration no pattern matches there is not seen. `ignored_files` lists the files this machine's build leaves out, whether they are tests, tool files such as `tool.go` or files for another platform such as `p_windows.go`.
- **A link to a regular file counts as the file it builds as.** The Go tool compiles a link named `x.go` that leads to a regular file, so `declarations`, `match` and `compare` read it too, under the link's own name, and an edit to its target moves the link's declarations. A link to anything else is skipped: a folder, as `./...` skips it, a broken link, which stops the Go tool itself, and a FIFO. A link that leaves the repo never gets this far, because the gate refuses the repo first.
- **A bad profile is told apart from a broken repo.** `goinspect` exits 2 for a patterns file it refuses and for a `main_package` that names nothing: a missing folder, a folder with no Go file for this build, a folder of another module, several packages or a file. ARDE raises a `ProfileProblem` for those, which goes back to Discovery as the submit tool's error, and for a repo with no route or a route it cannot read. Any other failure stops the run: a file that does not parse, an import nothing provides, a broken `go.mod`, or a `go.mod` that needs a newer Go. The Go runtime also exits 2 on a panic, so a failure counts as the profile's only with `goinspect`'s own mark at the start of the message. A package whose only problem is in one of its own files is the repo's, though a wrong `main_package` may be how ARDE came to read that file. Three cases do not fit. A library passes as `main_package`: `routes` reads it and the packages it imports, so the routes of the real `main` are left out with no line, and only `built_service`, which refuses a package that is not `main`, stops it. Two package clauses in one folder, and a `//go:build` line that does not parse, read as problems of the profile, though `go build` fails on both, so the baseline build stops the run first.
- **Params, env vars and error codes are read from literals.** A registered path with a host, such as `GET example.com/x`, stops the run. A param name, env name or error code that is not a string literal is dropped, a const included, and so is a literal that is not UTF-8, because JSON would turn two such literals into one text, so a repo that wraps `os.Getenv` in its own helper gets nothing from the default pattern, and Discovery has to supply one for that helper. Each dropped call is listed in the inventory's `dropped`, with its file and line. The call inside a helper that a pattern of the same kind matches is not listed, because that pattern reads the value at the helper's calls. A pattern that matched no call is named in `unmatched_patterns`. Neither shows a call that no pattern matched, so `dropped` is not a full account of what was missed.
- **Repo text in the inventory is one line, with a capped length.** A handler, param, env var, struct, field, JSON key or make target holds at most 200 characters, a declared type 500, a route path 1,000 and a file name 1,024, and none may hold a control character, a line or paragraph separator, a byte order mark, or a direction embedding, override or isolate, which would reorder what a reader of the source sees. The refusal names the code point and its offset. Every other format character is kept, such as a zero-width non-joiner as Persian writes, a zero-width joiner inside an emoji, a direction mark, a zero-width space or a soft hyphen, and a message shows each of them escaped. A function id holds at most 1,000 characters and a declaration id 1,234. A route that fails this stops the run with exit 3. A param, env var, error code, response field, make target or declaration id that fails it is left out and listed in `dropped`, without its text. An error code must also be a name a fact can carry, so the message in `http.Error(w, "not found", 404)` is no code and goes to `dropped`. A status keeps its first 80 characters on one line. A file name in a dropped line or an error is printed with its control characters escaped. The number of items is not capped, so a large repo gives a large inventory.
- **A struct declared inside a function, and an anonymous struct, are not response fields.** `declarations` reads top-level types only.
- **A json name is read as `reflect` reads it, and `encoding/json` then applies its own rules.** An escape in a tag decodes, and a name that is not UTF-8 counts as no name, so the field keeps its own, as `encoding/json` does. A name it refuses for another reason, such as one holding a quote or a backslash, is listed as written, though the reply carries the field's own name.
- **A `json:"n,string"` field keeps its declared type.** The inventory says `int` for a field whose reply carries a string.
- **`GET /{$}` and `GET /` are one route key.** ARDE writes the exact-root pattern `/{$}` as `/`, so the two read as one route. `route_fingerprints` gives such a key no hash when its functions differ, with the reason `shared key`, and the route counts as changed on every run.
- **A route's fingerprint covers every function of the service its handler names, and its anchor is one of them.** Those functions are the route's roots: the factory, the middleware, the handler and a function handed over as a value alike, such as `renderError` in `handleListItems(s, renderError)`, so an edit to any of them moves the hash. A route registered through a function that registers routes for its callers also roots at that function, whose code shapes every request, at every function of the service its site names, and at every function named in the call's arguments other than the path and the method, such as middleware the function applies: so editing `writeJSON` in a wrapper's `func(w, r) { writeJSON(w, load(r)) }` moves the route. A site inside such a function that registers a handler of its own and none the call gives, such as `preflight` at `"OPTIONS "+path` beside each route, reads as that handler, with its own anchor, roots and identity, and with the function that registers it and the functions named in the call's other arguments as roots too, because the site can still run middleware the call hands over. A function written in place in those other arguments leaves the route with no anchor and no hash, as one in the handler does. The hash also covers every constant the handler expression and those arguments hold, such as the `5` in `paged(5, h)`, because SSA writes it into the code of the function that holds the registration, which no route's hash covers. A route with one root and no such constant, such as one whose handler is a function's name, keeps that root's own fingerprint. The anchor, `handler_id`, is the function the route's docs belong on: the innermost handler when every call around it only wraps it, and otherwise the outermost function of the service that does more, which is a factory. A call only wraps when it is a conversion such as `http.HandlerFunc(x)`, a call to another module's function given one handler, such as `http.TimeoutHandler`, or a call to a function of the service given one handler that its body serves through: it calls the handler, calls or takes its `ServeHTTP`, passes the handler or its `ServeHTTP` to a call that returns a handler, or returns a composite literal of a type of the service with a `ServeHTTP` that keeps the handler in a field, such as `&headerMiddleware{next: next}`. So `logged(listItems)` anchors at `listItems` whether `logged` calls `next(w, r)` or `next.ServeHTTP(w, r)`. A call whose function is itself a call to a function of the service, as in `requireRole("admin")(h)`, `cors(opts)(h)` or `rateLimit(n)(h)`, only wraps when a function the first call returns wraps its handler by the same rules, and the function called first is a root. Middleware that stores its handler some other way, such as in a variable it fills and then returns, is a factory, and the docs go on it. A factory that falls back on a handler it is given reads the same as middleware, so a single route `spa(pages, notFound)` anchors at the fallback, `notFound`. The spec stays right, because swag reads only the comment above the function it is given. When two or more routes resolve to one anchor and their handlers differ by the functions they name, the variables they read or the constants they pass, compared by what they hold and not by their text, only the routes whose handler is the anchor alone keep it: the anchor's name or a method value of it, through conversions only, with no other root and no constant, such as `notFound`, `http.HandlerFunc(notFound)` or `s.items`. Every other route gets `handler_id` None, and `shares_anchor_with` names the routes whose handler differs from its own. One comment block would otherwise merge their operations in the spec, as `spa(shopPages, notFound)` and `spa(adminPages, notFound)` would on `notFound`, while `notFound` registered alone keeps it. Their roots and hashes stay. Routes whose handlers hold the same thing are one handler at several paths and keep the anchor however each is written. A method value's receiver counts by its type, so `s.items` registered from two methods whose receivers are two variables is one handler; a receiver of an interface type still counts by its variable. A handler is a function of exactly `(http.ResponseWriter, *http.Request)`, returning nothing or an error, or a value with such a `ServeHTTP`. A value of a type of the service that serves requests itself, such as `&itemsHandler{...}`, `itemsHandler{}` or a variable, a field or a table entry of that type, anchors at that type's `ServeHTTP` and roots there, and reads as the type's name, or as the variable as written. The roots also hold every method that an interface can call, as the walk counts them, of each type of the service that the handler hands to an interface: the handler itself where the registration takes an `http.Handler`, such as `apiFunc(s.orders)`, whose `ServeHTTP` is a root beside `s.orders`, an argument given to a parameter of interface type, and an element a composite literal keeps as one. A route has no anchor and no hash when its handler holds a function written in place, which reads as `(inline)` and has no id, or when the innermost handler is a local variable, a field, a package variable or a table entry of a function type or of an interface, a method of an interface, a value whose `ServeHTTP` comes from an interface it embeds, such as `logged{Handler: h}`, a function of another module, or a call the compiler cannot name, such as one through a variable. A handler called through a local variable that holds middleware, such as `admin(h)` after `admin := requireRole("admin")`, has no anchor either, because the docs would go on the middleware. When nothing writes the variable after its declaration, its roots are the functions named in the call's arguments and in what filled the variable, and the constants of both are in the hash. When something writes it again, it could hold anything, so the route has no roots. A route with no roots has the reason `inline` or `no function`, counts as changed on every run, and has no declaration to carry a swag block, so Task 14 gives it facts and docs and no block.
- **Middleware the handler does not name is outside the fingerprint.** So is middleware held in a variable, local or package, and handed on, such as the slice in `admin := []middleware{requireAdmin}` passed as `a.get("/admin/items", items, admin...)` or `chain(orders, admin...)`: the hash covers `a.get` or `chain` and the handler, and `requireAdmin` is named only where the variable is filled, so an edit to it moves neither route. A handler called through a local variable that holds one middleware, such as `admin(h)` after `admin := requireRole("admin")`, is the exception the paragraph above describes. Middleware around the whole mux, such as `logged(mux)` handed to `ListenAndServe`, is named at no registration, so an edit to it moves no route, and `declarations` reports it. A value made into an `http.Handler` before the registration, and handed to it as an interface, such as `var h http.Handler = &itemsHandler{}` and then `mux.Handle("/x", h)`, has no anchor, so its route has no hash and counts as changed on every run.
- **A Makefile that cannot be read stops the run.** Exit 2, for a file that is unreadable or over 1 MiB, because ARDE reads it itself with no timeout. A Makefile that is a broken link reads as no Makefile, with no make targets and no message.
- **Make targets come from a regex over the top-level Makefile.** A target that an included file defines, or that a variable builds, is missed.
- **`test_ok` says that no test failed, and `tests_run` says how many ran.** The tests run as `go test -json -count=1 -timeout 540s ./...`, and each test's end is read from the events. `tests_run` counts top-level tests that reached a pass or a fail. Every test and subtest that skipped is named in `tests_skipped`, and a parent whose subtests all skipped still counts as run. A package with no test files, or with its tests behind a build tag, adds to neither and exits 0, so `test_ok` is true with `tests_run` at 0, and `ignored_files` shows the tagged files. The Go exit code stays the verdict. A test cut off by an exit or a timeout has no end, so it is not counted, and the package fails. One exception was measured: a test that calls `syscall.Exit(0)` reads as a pass and the tests after it never run, which shows only as `tests_run` below `tests_listed`. That is a weak sign, because any benchmark does the same: it is listed and not run, so a clean run of a package with one benchmark gave `tests_run` 5 and `tests_listed` 6.
- **A repo that does not load is a red result, not an error.** With a broken `go.mod` or no `go.mod`, `run_checks` returns every check false and the toolchain's own words in `output`, with `tests_listed` at `None` and `ignored_files` empty. `build_ok` is also false when `./...` matched no packages, because Go exits 0 on that with nothing built.
- **The counts are only as honest as the tests.** Plain text a test prints is not read as a result, but a test that prints the control byte `\x16`, which marks the test runner's own lines, can add events. Measured: a repo with one failing test gave `tests_run` 2 and named a skipped test that does not exist. `test_ok` stayed false, because the exit code decides it. A test runs as the user anyway, so this gives a hostile repo nothing new, and `tests_run` is evidence about a repo you trust, not proof against one you do not.
- **`tests_listed` is what exists, not what ran.** It counts tests, benchmarks, fuzz tests and examples, and it is `None` when a test package does not compile, because a count of the rest would read as a total. A `TestMain` that leaves before `m.Run` lists nothing and runs nothing.
- **A test sees the allow-listed environment and the Go variables, and nothing else.** A test guarded by a variable outside them, such as a database URL, skips or fails under ARDE and may pass in your shell, even with the variable exported. An extra test command gets the same environment, so it has to set the variable itself: `env DATABASE_URL=... go test ./...` in `extra_test_commands` ran such a test.
- **A nested module is not checked.** `./...` stops at a folder with its own `go.mod`, so build, vet and test never reach it, even when the repo's own `go.work` names it. Each such folder is named in `unchecked_modules`, the outermost only, so a failing test there cannot turn a run red. One inside `vendor`, `testdata` or a folder starting with `_` or `.` is not named, because `./...` never looks there for anything.
- **Go's clock is per test binary, and ARDE's is for the whole command.** Go stops a binary after 540 s, prints the tests still running and fails the package, so one hang is a red result that names the test. ARDE stops `go test` after 600 s, so slow packages that run one after another can reach that first, and that stops the run. A timeout's message then holds the last 2,000 bytes the command printed, which for `go test` are events, and in a repo of many packages may be little, because `go` holds a package's output until it ends.
- **Extra test commands run without a shell.** They are split into words, so `&&`, pipes and redirects do not work in them.
- **swag passes over every folder named `docs`, and every hidden folder.** A handler declared in one gets no operation in the spec, and swag still exits 0. Measured for a `docs` folder with v2.0.0-rc6, and read in its source for a hidden one. `SpecMatchesInventory` reports such a route as missing from the spec, owned by code when the wiki has its fact, so the run stops and names the handler's file.
- **A repo's `.swaggo` file shapes its spec.** swag reads type overrides from that file in the repo root, so a line such as `replace birds.Nest string` turns that struct into a string wherever the spec uses it, and swag still exits 0. ARDE runs the pinned command as it stands and leaves the file in place. Measured with v2.0.0-rc6.
- **No detection of critical changes** that alter a project's scope or can damage a service while the tests still pass.
- **No stored knowledge graph.** It was dropped. Only cross-repo questions such as "which services use this contract?" would reopen it.

- **Routes that change data are documented from code alone.** Explore probes with GET and HEAD only, because a request must not change what the service holds, and the port's type allows no other method. A POST, PUT, PATCH, DELETE or OPTIONS route is found, read and given its params and error responses, but its success response can't be backed: a 2xx needs a probe that returned it. Its spec entry has no success status or reply body, and the live checks never call it.
- **Request bodies are not in the inventory.** Params come from query, path, form and header readers. A JSON body a client sends, read with `json.NewDecoder(r.Body).Decode`, is not extracted, so the spec doesn't describe it.

- **ARDE starts only the Go binary.** It builds the main package and runs it on a free port, with no database, cache or other service it may need. A service that needs one to start, or to answer correctly, fails at Explore or is documented as it behaves without it. ARDE does not read the repo's own compose file.

## Discovery and the profile

- **The live route check sends one GET per path, with each wildcard filled with `1`.** `validate_profile` flags a route that answers exactly as a path that cannot exist does: the same status, content type and body. A false alarm is a handler that answers that value the way the service answers a missing path, for example with `http.NotFound`. Also flagged are a root catch-all wildcard that answers every path alike, and a mount's own path, such as `ANY /users/`. `/` is not compared. A route on a mux nothing serves is missed when the 404 body quotes the path that was requested. A route that gives no answer within 10 s is not flagged.
- **The live route check runs on a saved profile only.** The pipeline calls `validate_profile` at the start of a later run. A freshly discovered profile is not started before Explore, so on a first run a dead route is not flagged there, and a wrong port variable exits 1 at explore, not 3.
- **A saved profile is checked again on every run.** A route that answers like a missing path makes Discovery run, and cost money, every time.
- **Discovery checks `main_file` only as a file of the service.** A file in the service that holds no entry point is caught at the render.
- **Any start failure is a finding for Discovery, a log path ARDE cannot write included.** The runner does not tell those causes apart.
- **An inventory over 1 MiB of JSON stops the run with exit 2.** The largest real service measured was 12 KB.
- **A repeated key in `profile.override.yaml` is not refused: the last one wins.**
- **A `profile.yaml` of another `schema_version`, or with none, is replaced by the next Discovery.**

## Facts

- **The default param patterns match by text.** The Go adapter reads `URL.Query().Get`, `PathValue`, `FormValue`, `PostFormValue` and `Header.Get` on any one identifier with no pattern. A request held in a struct field, as in `s.req.URL.Query().Get`, is not read, and a `Header.Get` on an HTTP response the service reads as a client is listed as a param.
- **Each response status needs its own evidence.** A status must be returned by a probe the fact cites, or, at 400 or above, be the status of an error code the response lists. An error code's status counts only when the source writes it as a number or as a `net/http` constant named through `http`; a variable, a call or another import name needs a cited probe.
- **A code quote proves only that the code exists, not that it supports the fact.** Quotes match with each run of whitespace read as one space, from the first 1 MiB of a file.
- **Only Go source the service is built from (the files the inventory's declarations name), its module files at the repo root and the root Makefile make reads count as source.** Test data, vendored code, build-ignored files, other programs, `*.mk` files, a README, YAML or a Dockerfile are never evidence. In the Makefile, a line is free text from its first `#` or quote through its continued lines. A quoted path must be written as `list_files` writes it.
- **A probe proves only what the service returned.** Planted text in a reply can still back a rule.
- **Every response field needs a field fact,** even in a struct no handler replies with, because nothing tells which structs a handler reaches.
- **Env vars and make targets are outside coverage.**
- **Unqualified response types are not checked.** A qualified one, and every variant of a polymorphic field, must name a struct of the inventory.
- **`suspected_injections` holds only what an agent chose to report.** Discovery, Explore and the docs agent each name the text that tried to direct them. A model that was steered and did not say so leaves no warning.
- **The wiki is saved file by file.** A crash between files can leave a fact in two topics, which stops the next load.

## The docs

- **A page ARDE would write that someone else wrote stops the run.** If the target already has, say, docs/architecture.md without ARDE's first line, the run stops with exit 2 before any model call and asks for the file to be moved.
- **A repo with no `README.md` gets no link to its docs.** ARDE appends to a README a person wrote and does not write one, so a `README.rst` is not edited.
- **A section goes stale through its facts, not its words.** `sections.yaml` records the section's own topic's facts and those the agent says it used. A fact the agent drew on but did not list does not make the section stale. The overview and the change guide rest on every fact, so any fact that comes or goes rewrites them. Each section's agent sees every fact, so its input grows with the wiki.
- **The docs agent sees a probe body cut at 2,000 characters.** It is told when a body is cut and not to show it as whole. Checking examples against the service is the docs checks' job.
- **Fact text in the API reference is escaped only where it would break the page:** a pipe, a backslash and `<`, and the first mark of an endpoint's summary, which stands as a paragraph of its own. Other Markdown in a description, such as a link, renders as Markdown, and the grounding check owns URLs.
- **The API reference reads a field's JSON type from its declared type alone.** A named type with no struct in the inventory, such as `type Category string`, a type of another module, a generic instance or `any`, is shown by its name rather than its JSON kind. A struct with its own `MarshalJSON` or `MarshalText`, and a field tagged `,string`, are shown as declared, which is not what the service sends. A pointer without `omitempty` is shown as always present, though it may be `null`.
- **A bare response type is read in the package of the route's `handler_file`.** A route with no single handler function has none, so its bare type is shown by name. A qualified type must name one struct of the inventory by its package's name. Error bodies are grouped by struct, so two structs that answer one status on different routes read as two groups for that status.
- **A reply body is expanded 8 structs deep.** Past that, and where a struct holds itself, a field is shown by its type's name. A struct a body holds twice is expanded twice, as `unit_price.amount` and `total.amount`. A struct no endpoint reaches is listed under "Other reply structs" with its own fields, and every struct it holds is named, not expanded.
- **An example is one recorded reply,** the first probe of the endpoint with that status whose body is a JSON object or array, from those the endpoint fact cites first. A probe belongs to the endpoint by its method and its path, a wildcard matching one segment, so a subtree route such as `GET /` matches only `/`. With no such probe there is no example. Past 40 lines, each array is cut to its first 2 items.

## Checks

- **The allow-list counts lines, it does not place them.** A line that only moved is not seen. The code comparison sees moved code, but a directive moved, for example below the package clause, is seen by neither.
- **On a checkout with CRLF line endings, the formatting check tests nothing.** `gofmt -l` lists every Go file with CRLF line endings, so on such a checkout, as `core.autocrlf=true` makes, every Go file is flagged before the run and none can be newly flagged after it. Measured on such a checkout of `catalog-poc`: 10 of 10 Go files flagged in both copies. The renderer keeps a CRLF file CRLF throughout, and the behaviour check still runs. The fix is to ask gofmt about each file's LF form, as the renderer already does.
- **The edit checks read Go files and module files only.** A changed embedded file, C or assembly source is not seen. ARDE writes none, except the spec, if a service embeds its docs folder.
- **The tag rule reads the first raw string on a line.** ARDE's pairs added to a raw string in code pass the allow-list, and the code comparison catches them.
- **Replies must match in status, content type and body.** A service whose reply holds the time or a random id fails Behaviour on every run.
- **Only recorded probes and placeholder-free routes are requested before and after.** A change on any other path is left to the code comparison.
- **The live check sends a path param only outside its bounds.** A value inside them may name nothing, so a minimum that is too low for a path param is missed.
- **The live check starts from a probe that succeeded.** An operation that documents a 2xx but has no successful probe is a finding. An operation with another verb than GET or HEAD, and a header or cookie param, is never requested.
- **A default is checked by comparing the status and body of two replies.** A reply that holds a time or echoes its query differs, and is reported.
- **A part of an `allOf` that is a reference is closed by its own schema**, so it refuses keys that another part adds. ARDE renders no composition.
- **Docs grounding is a heuristic layer.** It reads Markdown by hand, so a fence under a list item, other HTML tags such as `<samp>`, keys of data blocks, and a value matched as a substring of a probe body can pass it. It backs up the evidence rules and the docs agent's facts-only view; it is not a parser-exact guarantee.
- **Only a command the owner added to the profile counts as grounded from the profile.** A command Discovery reports is a model's output, so a docs command found only there is a finding. Commands in the README, a Dockerfile, a CI file or a Makefile are grounded.
- **Docs grounding recognises a host in a URL, a link, an e-mail address, before a port or after `www.`.** A bare `example.com` in prose can't be told from `main.go`. A URL or link must appear in the repo or a probe body exactly as written, after entities are decoded, or lead to a file of the output copy.
- **Every line of every code block in a page the run wrote is read as a command**, output and comments included. The only exception is a `json`, `yaml` or `toml` block that parses as such and whose every text value appears in the repo's text or a recorded probe body, as written or, in a JSON body, as its escapes decode; YAML that uses an alias is never exempt. A JSON block must be an object or array, and a YAML block a mapping. Keys are not checked. A `go` or other source block is always read as commands, so a code quote in the docs is a finding.
- **A page the run wrote that holds a code block in a blockquote, or an HTML `<pre>` or `<code>` tag, is a finding.** ARDE's docs never use either.
- **A page the run wrote that is over 1 MiB, holds a NUL byte, cannot be read or is a link is a finding.**
- **Markdown is read by hand, with no library.** An indented line after a blank line counts as code, even where a list makes it a paragraph. That errs toward a finding.

## The repair loop

- **The early stop compares findings by check and subject.** A round that fixes one of two problems a check reports on one subject, such as one reply, reads as no progress and ends the loop. The message is left out because it can name the request that showed the problem, which changes when explore probes again. With one round, the default, the early stop never fires.
- **A docs repair rewrites every section the docs writer would write, not only those a finding names.** On a first run that is every section. A section the writer would keep is not rewritten even when a finding names it, which can happen only when its page was missing from the repo.
- **A repair round writes the whole output again.** Even a docs-only round repeats the render and swag, and rebuilds and restarts both services. That costs no model call beyond the docs sections, but costs seconds per round.
- **A topic explore changed in a repair is rewritten even when the repair restored the fact the last run saved**, at the cost of one docs run that the restored page did not need.
- **The pipeline is tested with one round.** More rounds are tested only on the loop itself, in `tests/application/test_repair.py`.

## Sources

- **A local path must be the top folder of its git repo, with at least one commit.** A service in a subfolder of a larger repo is refused, and the message names the top folder. A folder that is not a git repo is refused too, with `git init` as the next action, because each run records the commit it starts from.
- **`--branch` works only with a URL.** A local repo is copied as its working tree stands, uncommitted and untracked files included, so the branch to document is the one checked out.
- **Submodules and repos nested inside a local repo are left out of the copy**, because git lists none of their files. A clone from a URL fetches no submodules either.
- **A local repo is untrusted input, `.git` included.** It may be an unpacked archive. So git runs with `core.fsmonitor` off, because `git ls-files` ran the command a repo's own settings named (measured). An index entry that git itself refuses to add, such as `../x`, an absolute path or one inside `.git`, stops the run, because `git ls-files` prints whatever an index holds (measured). A path below a linked folder is left out, as git counts it deleted: copied through the link, it was read from outside and written outside the copy (measured). A file that is neither a regular file nor a link, such as a pipe, stops the run.
- **Every link in a local repo is checked before git runs, ignored files and `.git` included.** A `packed-refs` linked to a file outside put that file's line in git's error (measured), and a link in `.git` can lead to a folder of the repo that holds a link out. So a link that leaves the repo stops the run even when git ignores it and the copy would leave it out, such as a `.env` linked to a shared file: replace it with the file, or move it out of the repo. A folder the walk cannot read stops the run too, ignored or not, and the walk reads every ignored folder, however large. A hook linked to a script inside the repo passes.
- **A `.git` that is a file is not followed.** In a worktree or a submodule, `.git` is a file whose `gitdir:` line names a folder elsewhere, and that folder is not checked for links.
- **Two names that are one path once case and Unicode form are ignored stop the run**, such as `A` and `a/x`, or `café` composed and decomposed. On a disk that ignores case, as macOS does by default, `a/x` would be written through a link `A`, even where the repo's own disk tells them apart. The copy also writes every file before it makes any link.
- **A file name that is not UTF-8 is copied by its bytes.** git prints such a name escaped, and the copy decodes it. Measured on Linux, in the container, for a tracked and an untracked name. macOS refuses such names, so the test skips there.
- **A clone gets no SSH agent.** Git runs with the allow-listed environment, which leaves out `SSH_AUTH_SOCK`, and it never prompts. A key that needs a passphrase cannot be used, so use HTTPS with a credential helper, or clone the repo yourself and pass its path. This is reasoned, not tested.
- **A URL needs a scheme, as in `https://`, or the `user@host:path` form.** Anything else is read as a local path, so `host:path` without a user is not found, and git's other transports, such as `ext::`, which runs a command, are never used.

## Workspaces and re-runs

- A fork has a different URL, so it gets a new workspace and a full first run. The spellings of one remote share a workspace: over HTTPS or SSH, with or without a user, a password, `.git` or a trailing slash, and a local clone shares the workspace of its `origin`. A local repo with no `origin` gets a workspace per folder path, so moving it means a full first run.
- A second branch in the same workspace counts as a change from the last successful run.
- **Line endings count as a change.** A checkout made with `core.autocrlf=true` holds CRLF where the remote holds LF. So a local run after a URL run of the same repo, or the reverse, sees changed files where nothing changed, and Explore re-checks the facts linked to them. Measured on `catalog-poc`: 16 of 16 files differed by carriage returns alone, and the 6 that are not Go files counted as changed, as no Go declaration did. 2 facts went stale and Docs rewrote 4 pages, for $0.76 and 93 s. Use one kind of source for a repo, or clone with `git clone -c core.autocrlf=false`.
- Each URL run clones afresh into the workspace. The workspace keeps that clone and the one before it, and removes older ones. The snapshot keeps the one before it on disk too, so a workspace holds up to two copies of each. Nothing removes the folders under `runs/`.
- The wiki is not exported into the target repo. A later `--export-wiki` flag could write a readable one-way copy.
- A re-run always runs Explore, even when nothing is stale. A request that now gets another answer is not detected before Explore runs.
- A repo's own file removed from the `docs` folder is not counted as a change, because ARDE writes its pages and the spec there.
- A local path run writes nothing to the user's repo and commits nothing. Its result is the output copy in the run folder, because write-back is not built.
- The commit force-adds ARDE's paths, including ones the repo lists in `.gitignore`.
- Nothing locks a workspace, so two runs on one repo at the same time can clash.

## The judge

- **Two real runs, both on `catalog-poc`, and no measured catch rate.** The deliverable run's judge predicted all 20 replies right, for $0.29. The container run's judge made one mismatch, a leading `+` in `qty`, and a fresh re-test cleared it as noise although the docs did mislead there; its clarity note named the sentence. The tests script the model's replies, and no eval asserts what the judge finds. How often it catches a wrong page, how often a re-test clears a real gap, and what it costs on a larger service are unknown.
- It cannot test rules that have no HTTP effect. On a later run it must try only the routes, params and error codes that the changed facts link, so a changed rule fact that links only declarations is not judged, and a run that changed no such fact runs no judge.
- An arithmetic slip looks like a mismatch, and a lucky guess passes. A prediction counts as one only for the status and the fields the judge chose to predict, so a judge that predicts little proves little.
- The prompt asks the judge to predict what the docs state even after a reply has shown otherwise. A model that learns from the replies instead hides a gap in the docs, and nothing in code can tell.
- An error code is exempt as unreachable only if the wiki holds an `unreachable` fact with code evidence. A wrong claim of unreachable is a known limit.
- **It sends GET and HEAD alone, with no headers.** A route of another method, its params, a header param, and an error code that only such routes return are exempt, each listed in `RunReport.exemptions`. The console summary does not print the exemptions; `report.json` and `--json` hold them.
- **What a request tries is read from its method and path alone.** A route is tried by a request of its own method, or any for `ANY`, whose path matches the pattern with a wildcard matching one segment, so a subtree route such as `GET /` is tried only by `/`, and a HEAD does not try a GET route. A query or form param is tried by a request to its route whose query names it. An error code is tried by a reply of status 400 or above whose body holds the code as a whole word.
- **A field is named by a dotted path of keys and array indexes**, so a key that holds a dot cannot be predicted. Values are compared with their JSON type: `true` is not `1`, and `"1"` is not `1`. Numbers are compared as Python reads JSON, so two numbers that differ only past a float's precision compare equal.
- The judge is told the names of the items it must try. Each is in the API reference, which code renders from the same facts, so the list adds no name the docs do not hold.
- **A re-test sends the request again.** A reply that changes between the two, such as one that holds the time, can confirm a mismatch or clear one by chance. Each distinct request is re-tested once, as a fresh agent run that reads every page again, so a judge with many mismatches costs as many runs.
- A run whose last wiki holds facts is judged as a later run even when its snapshot is gone and every page is written again.

## Cost

- **The cap can be overshot by one call.** A call's price is known only after it is paid for. The run stops once spending reaches the cap, but the last call can pass it by its own cost: at the shipped settings the worst single Opus 5.5 call costs $4.32, from 1M uncached input tokens and 16,000 output tokens.
- **A stream that breaks is charged only for what it had reported.** The first event says what the prompt used, so those tokens reach the trace and the cap. Output tokens arrive in the last event, so those written before the break are missing and the total reads low. A failure before the first event has nothing to charge. That the real API's first event carries the prompt's tokens comes from the SDK's types and has not been seen live, and that such a call is billed is assumed, not measured against a bill.

## The model API

Measured against the live API on 2026-11-02, with Opus 5.5.

- **Every request streams.** The SDK refuses a call that does not stream above about 21,333 `max_tokens`, and thinking counts against that limit. A dropped stream is not retried, because the SDK retries only before a stream starts, so it ends the run with a next action. See [decision 0011](decisions/0011-stream-every-request.md).

- **Strict tool use is refused for the repo profile and for the facts.** The API answers `For 'object' type, 'additionalProperties: object' is not supported` for the open `args` dict in the profile, and `Schema type 'oneOf' is not supported` for the fact union. Rewriting `oneOf` as `anyOf` did not help on Haiku 5.5: the API then said the compiled grammar was too large. Tools with these schemas must be sent with `strict=False`, and code validation holds the guarantee.
- **A refusal ends the agent, with no retry on another model.** The server-side fallback needs the beta client, and Haiku 5.5, which the classifier uses, has no fallback at all. The agent stops with the reason `refused`. The category and explanation go to `model_call` and `debug.log`, and `AgentStopped` exposes the category, so false positives can be counted on the first real run. No live refusal has been seen yet, so this rests on the SDK's types.
- **An error result with no text is refused by the API** (HTTP 400). The agent loop sends a stand-in text, so a tool that fails silently does not end the run.

## Not tested yet

Move an item out of this list when a test or a measurement covers it. What the real runs on `catalog-poc` and the hostile fixture measured is in [the first real runs](decisions/first-real-run.md).

- Windows and amd64 hosts, and a Linux host outside Docker Desktop. `make check` and `make integration` pass in the image on Linux arm64, in Docker Desktop's VM, and the container's own tests ran there. No run used a Linux host's own bind mount: a volume owned by another user stood in for one.
- The container on a real model. Every run in the image used scripted model replies. A scripted run on `catalog-poc`, cloned over HTTPS inside the container, passed its baseline build, vet and tests on Linux, and stopped where the script, written for the shop fixture, ran out.
- No-config onboarding beyond `catalog-poc` and the fixtures. The one measurement on other real services is from before the routes rework: 3 of 10 plain `net/http` samples stopped with no way past. That figure is not re-measured, because `routes` compiles what it reads and third-party code is not compiled here.
- A repair round on a real model. Every real run so far passed its checks with no repair, or stopped before the repair loop was built.
- A SIGTERM sent to `uv run` rather than to `arde`. The signal test runs `tests/scripted_arde.py` as a process of its own, and `uv run` may not pass the signal on. The container runs `arde` itself, with no `uv run` in between.

## Known costs

- Behaviour runs the repo's build, vet and tests again on the output copy, once per attempt.
- The judge runs on every attempt whose code checks pass, on up to 30 turns, with every page and the spec in its first message, and each request it predicts wrong costs a re-test that reads them all again.
- Any changed fact rewrites the overview and the change guide, which costs two docs-agent calls on every re-run that changes a fact.
- **A one-line edit can make most of the wiki stale.** A fact goes stale when a declaration, route or file it links changed, and field facts link the route that replies with their struct. Measured on `catalog-poc`: changing one error message in the product handler staled 37 of 60 facts, and Explore submits each again. The answers stay right; the cost is time and tokens.
- **A workspace keeps only the last two clones.** An older run's result branch goes with its clone, so a result to keep is exported right after its run.
- `swag` v2.0.0-rc6 is a pre-release. It is pinned, and the run's checks would surface a bad spec.
- The first build of `swag` needs the network, unless the Go module cache already holds its modules. `tools/swag/go.sum` holds the hash of every module the build needs, so Go refuses a download that does not match. The binary prints its version as v2.0.0, because that is the string rc6 carries.
