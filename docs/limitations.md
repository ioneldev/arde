# Limitations

What ARDE does not do, and what has not been tested. Most of it comes from the [design](superpowers/specs/2026-11-01-arde-design.md). The writable-mount risk was found later, in a security review of the container experiment. Add to this page when you find a new limit.

## Trust and containers

- **Repos must be trusted.** The repo's code runs in the same container as ARDE and the API key. Removing `ANTHROPIC_*` from child processes limits accidents, but it is not a security boundary: code running as the same user can still read the parent's environment. The security review measured this on macOS: a child with the allow-listed environment read a stand-in value from the parent's starting environment through `KERN_PROCARGS2`, and a value the parent set after it started did not show.
- **A writable repo mount is an open risk.** The container mounts the local repo so it can write results back. Repo code running in the container could use that mount to tamper with the host repo, for example by planting a git hook that later runs on the host. This must be resolved before the container ships (Task 28 of the plan).
- **The `/data` volume is shared across repos.** The container keeps `ARDE_HOME`, `GOCACHE` and `GOPATH` in one volume, owned by the same user as repo code. Repo A's tests could write repo B's `profile.override.yaml`, the file `extra_test_commands` trusts, or, with `HOME` in that volume, the `go env` file the probe reads, and so set `GOPRIVATE=*` for repo B's checksums. This is reasoned, not tested, and must be resolved before the container ships (Task 28 of the plan).
- **Go commands read three settings from the user's `go env` file, and nothing else in it.** ARDE sets `GOENV=off` for every Go command, because that file lives under `HOME` and can hold a `GOFLAGS` with `-toolexec`. Once per process, in the parent, it asks `go env` for `GOPRIVATE`, `GONOPROXY` and `GONOSUMDB`, with the exported values of those three and the user's `XDG_CONFIG_HOME` and `GOENV` so that it looks where the user's own `go` looks, and it passes the answer on as Go gave it. Go decides which value wins and derives `GONOPROXY` and `GONOSUMDB` from `GOPRIVATE`, so a private repo builds and its module paths stay off the public proxy and checksum database. A `GOPROXY`, `GOSUMDB` or `GOTOOLCHAIN` that only the file holds is ignored on purpose, so a poisoned file cannot redirect where modules come from or switch the toolchain: every command runs with `GOENV=off`, and the probe itself runs with `GOTOOLCHAIN=local`, so neither the file nor a `go.mod` above the temporary folder can make it start or download another toolchain. Export anything else you need. An empty exported value counts as not exported. Those three settings can weaken checksum checks for the paths they name, which is why repos must be trusted. If `go env` fails or leaves one of them out, the run stops, because going on without them would send private paths to the public proxy.
- **A link that leads out of a repo stops the run.** Every `GoAdapter` method that takes a repo first walks all of it, `.git` included, and refuses any link whose real path is outside the repo's real path, with exit 2. The message names the link and never its target. This holds for every file, because the Go tool follows links and quotes a `go.mod` it cannot parse, and a repo's `go.work` can name a module inside `.git`. So a hook linked to a shared folder stops the run too, and the next action is to replace the link with the file. A hard link looks like a file, so it passes, and a clone does not create one. The walk runs once per call, when the method starts. A process the repo left running can plant a link after that, such as a test's child that outlives `run_checks` or the service Explore runs, and a later Go command in the same call can then quote the file the link points to. That process is repo code, which could read the file itself.
- **A repo cannot choose its toolchain unless you let it.** Every Go command runs with `GOTOOLCHAIN=local` unless you export another value, so a `go` or `toolchain` line in `go.mod` can neither start a program found on `PATH` nor ask for a download. The cost is that a repo that needs a newer Go than the one installed stops with Go's own error, such as `go.mod requires go >= 1.99.0`, and `goinspect` itself needs the Go version in its own `go.mod`. Export `GOTOOLCHAIN=auto` to accept the switch.
- **A relative `PATH` entry is removed from every child's environment.** A child changes folder before it looks for a program, so `.` or an empty entry would find a `go` the repo planted. When nothing absolute is left, `PATH` is left out and the system's default path applies, because an empty `PATH` reads as the current folder.
- **A repo decides its own workspace, and nothing above it can.** Every Go command and `goinspect` run with `GOWORK` set to the repo's own `go.work` when that regular file exists, and to `off` otherwise. Without this, Go looks in every folder above the repo, and a `go.work` planted there chose the code that was built and run. An exported `GOWORK` is ignored.
- **A timeout cannot reach a grandchild that started its own session.** The child and its process group are killed, and ARDE stops waiting. A daemon that a test or an extra command started on its own keeps running.
- **If ARDE itself is killed with SIGKILL, SIGTERM or SIGHUP, a running service is left behind.** The service runner stops the service in a `finally` block, which covers a normal exit, an error and Ctrl-C. SIGKILL gives no code a chance to run, and that will stay so. SIGTERM and SIGHUP leave the service behind too, until the CLI installs its handlers for them in Task 17: Python has no handler for either by default, so no `finally` runs. The service keeps its port and its process group until someone stops it. To find it, look in `ps` for a binary in a folder named `arde-service-` under the temporary directory, and kill its process group.
- **The service gets the grace period only through its leader.** The runner sends SIGTERM to the whole process group, waits up to 5 s for the first process to exit, and then kills the group. A worker that needs longer than its parent to shut down is cut off the moment the parent exits. A service that starts its own session is out of reach of the group, as for any child.
- **A free port is found by binding and closing, so another process can take it before the service binds.** The window is short. A service that loses the race normally exits at once and is reported with its log. If the other process opens the port and answers, the first probe connects to it and the body starts against the wrong process. The service, which could not bind, exits, and the runner reports that as a `ServiceDiedError` with its log when the body ends.
- **A Ctrl-C that lands inside or just after the `Popen` call leaves the service running.** The process exists before `Popen` returns its handle, so the runner has nothing to stop yet, and moving the `try` cannot close that. The window is the 6 ms or so the call takes, plus a median of 77 microseconds, at most 118, from its return to the `try`. A second Ctrl-C between entering the stop and its first signal does the same, in a median of 27 microseconds and at most 41, because the code that notes whether the service had already exited sits outside the stop's `try`. An interrupt raised at each of those points left the service running, measured on macOS at a load average of about 9 on 12 cores. An interrupt anywhere else in the start, the wait, the body or the stop leaves nothing running.
- **The runner connects to `127.0.0.1` only.** A service that listens on `::1` alone is not found, and fails with the timeout error, which says so.
- **Two services given the same log path overwrite each other's log.** Each start truncates the file it is given, so every service needs its own.
- **A service log has no size cap.** A service that prints without end grows its log without limit. Only the last 2000 bytes go into an error.
- **The child's process group is signalled just after the child is reaped.** Once the child is gone and its group is empty, the group id is free, so in theory a reused id could be hit. It needs a process id wrap to land in the window, and a group that still has a member keeps its id. Measured on macOS over 60 runs of each case with spies, at a load average of about 9 on 12 cores, from the reap to the last signal: for `run_child`, which sends one signal after a child exits, a median of 39 microseconds and at most 411. The service runner sends more: two after a normal stop, the last at a median of 50 and at most 81, and three when the service died while the body used it, the last at a median of 184 and at most 596, because the leader is reaped before the first signal. When it exited during start the log is read in between, so the last of its signals comes at a median of 624 microseconds and at most 829 after the reap.
- **A child's output is kept on disk while it runs, and a process that outlives the child can keep writing to it.** ARDE keeps the last 1 MB of a check's output, stops the run when the event stream of `go test -json` passes 64 MB, and refuses a `goinspect` reply over 64 MB. That stream holds every line a test prints, also from tests that pass, so a repo whose tests print tens of megabytes stops there, where plain `go test` would pass, with the end of the stream in the message. It is read into memory to be counted: a stream of 53.5 MB peaked at 359 MB, measured once on a fixture. A command that writes directly, such as an extra test command, still uses as much disk as it writes until it ends, and a process that started its own session can go on writing to the deleted file after ARDE has returned, where `du` cannot see it. `go test` is different: `go` holds each package's output in memory until the package ends, so a test that prints without end costs memory there before it costs disk. Processes in the child's own group are killed when it exits.
- **No sandbox for untrusted merge-request code.** A separate sandbox is a non-goal for now.
- **Child output in a message is short and shows no control character.** An error keeps the last 2,000 bytes of what a child printed. In those bytes and in `CheckResult.output`, each control character except a line break and a tab is written out as `\xNN`, and each Unicode line or paragraph separator and direction control, U+2028, U+2029, U+202A to U+202E and U+2066 to U+2069, as `\uNNNN`, so a test cannot rewrite the terminal's title, clear the screen, break a line or reorder the text a reader sees. `CheckResult.output` is not cut to 2,000 bytes: it keeps up to 1 MB per stream, because the repair loop reads it. For the tests that stream is readable text rebuilt from the events, without what a passing test printed, as plain `go test` leaves it out. A test can still print text that looks like ARDE's own section header, such as `== test (exit 0) ==`, so that text is data and code decides pass or fail from the booleans alone.

## Prompt injection and data

- **Repo text can steer the agents.** Comments, READMEs and test names reach the models as plain input. A poisoned comment can steer a fact or a sentence in the docs. Code limits what that can reach: an agent has no shell or write tools, and it cannot set a command to run. A rule with no HTTP effect still goes unchecked, so a false one can reach the docs. This is reasoned: no agent has run against a hostile repo.
- **What the agents read leaves the machine.** Whatever an agent reads goes to Anthropic, including any secret committed to the target repo, and it is also stored in `debug.log`. Run folders can be read by their owner alone.
- **A native run has no container.** With `uv run arde`, repo code runs as the developer, with access to the home directory and the credentials in it.
- **Redaction is exact match.** The tracer replaces the API key wherever it appears whole. A key that was encoded or split on the way in would pass through. Only `trace.jsonl` and `debug.log` go through the tracer: `report.json`, `service.log` and stderr do not.

## What it understands

- **Go `net/http` only.** Other frameworks and other languages are not supported. Go idioms sit behind one interface so a second language can be added.
- **Names in facts are ASCII and plain.** A struct, field, type or error code with a non-ASCII letter, a generic type such as `Page[Product]`, or a `map` or `interface{}` response type fails validation instead of being written into a comment or tag. A service that uses them cannot be documented until the shape is allowed in the domain models.
- **`extract_inventory` needs a repo that compiles.** `goinspect routes` reads the service through the type checker, and it cannot read a package that does not build. The pipeline's baseline checks prove the build first.
- **The inventory covers the service built from `main_package`, by import.** Only `main_package` and the packages of its module that it imports, directly or not, count. A param, env var, error or response field from any other folder of the repo is left out and listed in `dropped`. A route from there is listed in `dropped` only when a route pattern matched it, such as `cmd/admin/main.go:13: route outside main_package ./cmd/api`: a registration of `net/http` that no pattern names is found through the type checker, which reads this service alone, so it leaves no line. A plain struct or function there is left out with no line, because nothing about it was lost. `main_package` must name a folder here: `./main.go` passes the type and then stops with a message.
- **A path must be one the compiler knows.** A string literal, a const and a sum of consts are read. Anything else stops the run with exit 3, so a loop over a table of routes stops it. A site inside a function that a route pattern matches is the one exception, because the pattern reads the path at that function's calls. A function a pattern matches at one call counts at every static call to it, whatever the receiver is called, so a pattern cannot lose a route by naming too little.
- **A function that registers routes for its callers is read in three forms, and any other stops the run.** A route pattern that matches such a function is read at its calls, and a site inside it whose path is not a constant must build that path from the function's parameters in one of three ways: the path parameter alone, a constant method and a space before it, as in `"GET "+path`, or the method parameter, a space and the path parameter, as in `method+" "+path`, with the method's position given as `method` in the pattern's args. Each call then registers the path built the same way from its own constants, so the constant method wins over the function's name, and the method at a call must be a constant. Anything else stops the run with exit 3 and names the site: a prefix such as `"/v1"+path` or one held in a field, a suffix, a local variable, `path.Join`, or a call that hands the path to another such function. So does a call to such a function that registers no route there, because its handler is a mux or the function registers no path it is given. A function with two sites gives two routes at each call. In the first form the method comes from the path the call passes, as in `"GET /x"`, or else from the function's name, such as `get`, which `net/http` itself does not enforce.
- **A registration is found when the compiler can name its target.** Every static call to `net/http.Handle`, `net/http.HandleFunc`, `(*net/http.ServeMux).Handle` or `.HandleFunc` is a site, in any package the service imports. Two forms are not seen, and a route in either is lost with no message: a call through an interface, and a method value held in a variable, such as `add := mux.HandleFunc`. A route pattern on the call adds either one. A route that another module adds is not listed either, such as one registered in the `init` of a dependency, and `_ "net/http/pprof"` is the usual case: only the service's own module is read. A function held in a variable that wraps a registration cannot be a wrapper, because no pattern reaches a variable's body, so its site stops the run.
- **A route on a mux nothing serves is still listed.** Reading source cannot show which mux reaches `ListenAndServe`, so `http.HandleFunc` in a service that serves its own mux gives a route that answers 404, as does a second mux that is never served. This was measured on a fixture. The planned live check in Task 12 owns finding such a route.
- **A table or a switch behind one handler is not seen.** ARDE reads registrations, so what a handler does with a request is outside the inventory. Measured on a fixture: a handler that looks `r.URL.Path` up in a table of pages gives one `ANY /` route and no line in `dropped`, and a `ServeHTTP` that switches on `r.Method` gives one `ANY` route. A profile cannot express either shape.
- **Paths that something else changes are not resolved.** A call to `http.StripPrefix` in the service stops the run with exit 3, naming the place, whether it sits at the site, behind an import name, in a variable or in a helper. One exception: a direct call to `http.FileServer` or `http.FileServerFS` as its handler, resolved by type, does not stop. No route sits under a file server, so the site reads as a route with no function id, which counts as changed on every run. A variable that holds a file server, middleware or a conversion around one, and a function of the service with the same name all still stop. A function of the service that adds a prefix to the path it is given stops the run, as the line above on such functions says. Router groups in another framework are not seen either: in a Gin-style sample the matcher reported `/ping` for `/v1/ping`. The live check planned for Task 12 flags a route that answers like a path that cannot exist, and it is not built yet.
- **A handler of type `*http.ServeMux` is a mount, not a route, and so is one behind middleware that passes it on.** The routes on the mounted mux are listed with the paths they are registered under, which are the whole paths when nothing strips them. A mux given to a function of the service that does not pass it on, such as `routesPage(mux)`, is a route of that function. A mux returned as a plain `http.Handler` has that type at the site, so its mount reads as an `ANY` route beside the real ones.
- **The call graph is static.** It misses calls through interfaces and through function values it cannot name, such as one read from a struct field or a map. A closure is followed, because a reached function's closures count as reached. Stored requests are the backstop.
- **A fingerprint covers function bodies, not package state.** A package-level `var` or type, and a function that runs only to fill a `var` or inside `init()`, are outside it. `declarations` reports such a change but cannot say which routes it touches.
- **`changed_declarations` does not see imports.** An import is no declaration. Measured: swapping `html/template` for `text/template` gives an empty list, and so does adding `_ "net/http/pprof"`, which also leaves the inventory and every fingerprint as they were, though it adds routes to a service that serves the default mux. Only `compare` sees either edit, so a report on one names a file and nothing else.
- **A fingerprint sees one build.** A file excluded by build constraints on the machine running it is not hashed, so an edit behind a custom tag, or in `helper_linux.go` on a Mac, moves nothing.
- **Only Go source in the module is hashed.** Assembly bodies, files read through `//go:embed` and code in other modules, vendored ones included, are outside it.
- **Code of another module under the same path has no body to hash.** That is a nested module, a module that a `replace` points at, a plain dependency under the same path prefix, and a `go.work` member. A route that reaches one gets no fingerprint, with the reason `no body`, and counts as changed on every run. A `testdata/` or `_`-prefixed folder of the module itself is loaded and hashed when the service imports it.
- **A package const used only as an array length inside a type declared in a function is not in that function's fingerprint.** SSA prints the type by name, and the syntax holds only the const's name. `declarations` still reports the const.
- **Adding `oneOf` or `binding:"optional"` to an anonymous struct moves a fingerprint**, because the SSA listing prints the type with its tags. This only over-reports, and ARDE writes those tags on named structs.
- **A new instantiation of a generic handler moves that handler's fingerprint.** The walk starts from every instance of a generic root, so a new type argument adds code to it. This only over-reports.
- **Any edit to a cgo file can move a route that calls C**, even a comment, because cgo names its symbols from a hash of the file. This only over-reports.
- **`goinspect` does not print an expression that spans more than 1,024 bytes of source.** An argument, a struct field's type or tag, or a callee past that size reads `(too long to print)`, or `(too long to print).Get` for a chain, so a pattern on the end of a chain still finds the call. A handler written in place past that size is `(inline)`, and a string literal keeps its value. Printing nested calls costs the square of the file's size, so a small file could ask for gigabytes. What is left is linear in the source, with a high constant: about 170 times its size for a file made only of nested calls under the cap, which is worked out and not measured, so a very large hostile file still costs memory until the 120 s timeout or the 64 MB reply limit stops it. Hashing streams, so its memory does not grow with the dump. It still takes time proportional to nodes times depth, and the timeout stops that too.
- **Patterns match the callee as text.** An unanchored regex can match text inside a chained call, so anchor them.
- **`main_package` must be `.` or start with `./`.** Any other text could name a package outside the repo, such as `cmd/go` in the toolchain or a dependency's program. So a service whose `main` lives in another module cannot be named: Go also refuses a nested module named by `./path`. `./...` passes the type and stops at the check that a service is one package `main`. A path element that starts with a dot is refused, such as `./.git/x` or `./cmd/.hidden`, because the Go tool passes over such a folder.
- **Hand-edited `@` lines are overwritten** from the wiki on the next run.
- **`@version` renders as `0.0.0`**, because the repo has no source for it and ARDE will not invent one.
- **The comment-only rule is Go-only.**
- **The comment-only rule is an allow-list, so it answers "real" for much that is harmless.** Only ordinary comment lines (a whole line starting `// `, no directive form, no `/*` or `*/`) and the tags `oneOf` and `binding:"optional"` may differ. An edited block comment, an edited trailing comment, an added blank line, a doc comment written with `///`, any directive, a line holding `+build` or `Code generated`, a byte order mark on one side only, and a file over 8 MiB, which is never read, all count as real, and so does any comment edit in a file with `"C"` or `` `C` `` text, or in a `_test.go` file that holds the word `Example`. A list of dangerous forms could never be complete, and a wrong "real" costs a fraction of a cent while a wrong "comment-only" ignores a change.
- **A comment-only edit can still change a program that reads its own source or its own line numbers.** A file named by `//go:embed x.go` or `//go:embed *.go` is data to the program, and a comment added above `runtime.Caller(0)` moves the line it reports. No rule that looks at one file can see this.
- **An allowed tag is part of a type's identity.** `oneOf` or `binding:"optional"` on a named struct can stop an assignment to an unnamed struct, or a `~struct` constraint, from compiling, and `reflect` can read the tag back. ARDE's own tag edits go through the build check, and a hand edit of this kind reads as comment-only.
- **Embedded struct fields are not response fields.** Their fields are promoted into the parent's JSON object, and the inventory cannot say so. An embedded field with a `json` name is also left out, although Go treats it as a named field. Two structs with one name in different packages are both listed and told apart by their file and package, but a fact that names a struct by its name alone cannot say which one it means. The plan has Task 13 tell them apart by `ResponseField.package`, and that is not built yet.
- **A struct with no `json` tag is not a response field,** though `encoding/json` writes its exported fields under their own names. A struct counts once one of its fields has a `json` key, and then an exported field with no tag is listed under its own name.
- **The inventory includes files for other platforms and behind other tags.** `declarations` and `match` skip `vendor`, `testdata`, names that start with `_` or `.`, a folder with its own `go.mod`, and a file whose build constraint requires the tag `ignore`: the tag alone, or an `&&` with it, in `//go:build` or in any `// +build` line. Every other file stays in, because some build includes it. That covers a file for another OS, one behind a tag such as `e2e`, and one behind a negated tag such as `!windows`. A route is the exception, because the type checker reads this machine's build alone and the service built here has no such route: a route pattern that matches in `only_windows.go` gives a line in `dropped`, not a route, and a registration no pattern matches there is not seen. `ignored_files` lists the files this machine's build leaves out, whether they are tests, tool files such as `tool.go` or files for another platform such as `p_windows.go`.
- **A link to a regular file counts as the file it builds as.** The Go tool compiles a link named `x.go` that leads to a regular file, so `declarations`, `match` and `compare` read it too, under the link's own name, and an edit to its target moves the link's declarations. A link to anything else is skipped: a folder, as `./...` skips it, a broken link, which stops the Go tool itself, and a FIFO. A link that leaves the repo never gets this far, because the gate refuses the repo first.
- **A bad profile is told apart from a broken repo.** `goinspect` exits 2 for a patterns file it refuses and for a `main_package` that names nothing: a missing folder, a folder with no Go file for this build, a folder of another module, several packages or a file. ARDE raises a `ProfileProblem` for those, which Task 12 can send back to Discovery, and for a repo with no route or a route it cannot read. Any other failure stops the run: a file that does not parse, an import nothing provides, a broken `go.mod`, or a `go.mod` that needs a newer Go. The Go runtime also exits 2 on a panic, so a failure counts as the profile's only with `goinspect`'s own mark at the start of the message. A package whose only problem is in one of its own files is the repo's, though a wrong `main_package` may be how ARDE came to read that file. Three cases do not fit. A library passes as `main_package`: `routes` reads it and the packages it imports, so the routes of the real `main` are left out with no line, and only `built_service`, which refuses a package that is not `main`, stops it. Two package clauses in one folder, and a `//go:build` line that does not parse, read as problems of the profile, though `go build` fails on both, so the baseline build stops the run first.
- **Params, env vars and error codes are read from literals.** A registered path with a host, such as `GET example.com/x`, stops the run. A param name, env name or error code that is not a string literal is dropped, a const included, and so is a literal that is not UTF-8, because JSON would turn two such literals into one text, so a repo that wraps `os.Getenv` in its own helper gets nothing from the default pattern, and Discovery has to supply one for that helper. Each dropped call is listed in the inventory's `dropped`, with its file and line. The call inside a helper that a pattern of the same kind matches is not listed, because that pattern reads the value at the helper's calls. A pattern that matched no call is named in `unmatched_patterns`. Neither shows a call that no pattern matched, so `dropped` is not a full account of what was missed.
- **Repo text in the inventory is one line, with a capped length.** A handler, param, env var, struct, field, JSON key or make target holds at most 200 characters, a declared type 500, a route path 1,000 and a file name 1,024, and none may hold a line break or a control character. A function id holds at most 1,000 characters and a declaration id 1,234. A route that fails this stops the run with exit 3. A param, env var, error code, response field, make target or declaration id that fails it is left out and listed in `dropped`, without its text. An error code must also be a name a fact can carry, so the message in `http.Error(w, "not found", 404)` is no code and goes to `dropped`. A status keeps its first 80 characters on one line. A file name in a dropped line or an error is printed with its control characters escaped. The number of items is not capped, so a large repo gives a large inventory.
- **A struct declared inside a function, and an anonymous struct, are not response fields.** `declarations` reads top-level types only.
- **A json name is read as `reflect` reads it, and `encoding/json` then applies its own rules.** An escape in a tag decodes, and a name that is not UTF-8 counts as no name, so the field keeps its own, as `encoding/json` does. A name it refuses for another reason, such as one holding a quote or a backslash, is listed as written, though the reply carries the field's own name.
- **A `json:"n,string"` field keeps its declared type.** The inventory says `int` for a field whose reply carries a string.
- **`GET /{$}` and `GET /` are one route key.** ARDE writes the exact-root pattern `/{$}` as `/`, so the two read as one route. `route_fingerprints` gives such a key no hash when its functions differ, with the reason `shared key`, and the route counts as changed on every run.
- **A route's fingerprint covers every function of the service its handler names, and its anchor is one of them.** Those functions are the route's roots: the factory, the middleware, the handler and a function handed over as a value alike, such as `renderError` in `handleListItems(s, renderError)`, so an edit to any of them moves the hash. A route with one root keeps that root's own fingerprint. The anchor, `handler_id`, is the function the route's docs belong on: the innermost handler when every call around it only wraps it, and otherwise the outermost function of the service that does more, which is a factory. A call only wraps when it is a conversion such as `http.HandlerFunc(x)`, a call to another module's function given one handler, such as `http.TimeoutHandler`, or a call to a function of the service given one handler whose body calls `ServeHTTP` on it or passes it to a call that returns a handler. So `spa(pages, notFound)`, whose body calls `notFound(w, r)` itself, anchors at `spa`, and so does middleware written that way, or one that keeps its handler in a struct: the route's docs then go on the middleware. A handler is a function of exactly `(http.ResponseWriter, *http.Request)`, returning nothing or an error, or a value with such a `ServeHTTP`. A route has no anchor and no hash when its handler holds a function written in place, which reads as `(inline)` and has no id, or when the innermost handler is a local variable, a field, a package variable, a table entry, a method of an interface, a function of another module, or a call the compiler cannot name, such as one through a variable. Such a route has the reason `inline` or `no function`, counts as changed on every run, and has no declaration to carry a swag block, so Task 14 gives it facts and docs and no block.
- **Middleware the handler does not name is outside the fingerprint.** Middleware around the whole mux, such as `logged(mux)` handed to `ListenAndServe`, is named at no registration, so an edit to it moves no route, and `declarations` reports it. The same holds for the `ServeHTTP` of a named handler type such as `apiFunc(s.orders)`, which the handler names only as a type.
- **A Makefile that cannot be read stops the run.** Exit 2, for a file that is unreadable or over 1 MiB, because ARDE reads it itself with no timeout. A Makefile that is a broken link reads as no Makefile, with no make targets and no message.
- **Make targets come from a regex over the top-level Makefile.** A target that an included file defines, or that a variable builds, is missed.
- **`test_ok` says that no test failed, and `tests_run` says how many ran.** The tests run as `go test -json -count=1 -timeout 540s ./...`, and each test's end is read from the events. `tests_run` counts top-level tests that reached a pass or a fail. Every test and subtest that skipped is named in `tests_skipped`, and a parent whose subtests all skipped still counts as run. A package with no test files, or with its tests behind a build tag, adds to neither and exits 0, so `test_ok` is true with `tests_run` at 0, and `ignored_files` shows the tagged files. The Go exit code stays the verdict. A test cut off by an exit or a timeout has no end, so it is not counted, and the package fails. One exception was measured: a test that calls `syscall.Exit(0)` reads as a pass and the tests after it never run, which shows only as `tests_run` below `tests_listed`. That is a weak sign, because any benchmark does the same: it is listed and not run, so a clean run of a package with one benchmark gave `tests_run` 5 and `tests_listed` 6.
- **A repo that does not load is a red result, not an error.** With a broken `go.mod` or no `go.mod`, `run_checks` returns every check false and the toolchain's own words in `output`, with `tests_listed` at `None` and `ignored_files` empty. `build_ok` is also false when `./...` matched no packages, because Go exits 0 on that with nothing built.
- **The counts are only as honest as the tests.** Plain text a test prints is not read as a result, but a test that prints the control byte `\x16`, which marks the test runner's own lines, can add events. Measured: a repo with one failing test gave `tests_run` 2 and named a skipped test that does not exist. `test_ok` stayed false, because the exit code decides it. A test runs as the user anyway, so this gives a hostile repo nothing new, and `tests_run` is evidence about a repo you trust, not proof against one you do not.
- **`tests_listed` is what exists, not what ran.** It counts tests, benchmarks, fuzz tests and examples, and it is `None` when a test package does not compile, because a count of the rest would read as a total. A `TestMain` that leaves before `m.Run` lists nothing and runs nothing.
- **A test sees the allow-listed environment and the Go variables, and nothing else.** A test guarded by a variable outside them, such as a database URL, skips or fails under ARDE and may pass in your shell, even with the variable exported. An extra test command gets the same environment, so it has to set the variable itself: `env DATABASE_URL=... go test ./...` in `extra_test_commands` ran such a test.
- **A nested module is not checked.** `./...` stops at a folder with its own `go.mod`, so build, vet and test never reach it, even when the repo's own `go.work` names it. Each such folder is named in `unchecked_modules`, the outermost only, so a failing test there cannot turn a run red. One inside `vendor`, `testdata` or a folder starting with `_` or `.` is not named, because `./...` never looks there for anything.
- **Go's clock is per test binary, and ARDE's is for the whole command.** Go stops a binary after 540 s, prints the tests still running and fails the package, so one hang is a red result that names the test. ARDE stops `go test` after 600 s, so slow packages that run one after another can reach that first, and that stops the run. A timeout's message then holds the last 2,000 bytes the command printed, which for `go test` are events, and in a repo of many packages may be little, because `go` holds a package's output until it ends.
- **Extra test commands run without a shell.** They are split into words, so `&&`, pipes and redirects do not work in them.
- **No detection of critical changes** that alter a project's scope or can damage a service while the tests still pass.
- **No stored knowledge graph.** It was dropped. Only cross-repo questions such as "which services use this contract?" would reopen it.

## Workspaces

- A fork has a different URL, so it gets a new workspace and a full first run.
- A second branch in the same workspace counts as a change from the last successful run.
- The wiki is not exported into the target repo. A later `--export-wiki` flag could write a readable one-way copy.

## The judge

- It cannot test rules that have no HTTP effect.
- An arithmetic slip looks like a mismatch, and a lucky guess passes.
- An error code is exempt as unreachable only if the wiki holds an `unreachable` fact with code evidence. A wrong claim of unreachable is a known limit.
- It has not been run yet, so its catch rate is unknown.

## Cost

- **The cap can be overshot by one call.** A call's price is known only after it is paid for. The run stops once spending reaches the cap, but the last call can pass it by its own cost: at the shipped settings the worst single Opus 5.5 call costs $4.32, from 1M uncached input tokens and 16,000 output tokens.
- **A stream that breaks is charged only for what it had reported.** The first event says what the prompt used, so those tokens reach the trace and the cap. Output tokens arrive in the last event, so those written before the break are missing and the total reads low. A failure before the first event has nothing to charge. That the real API's first event carries the prompt's tokens comes from the SDK's types and has not been seen live, and that such a call is billed is assumed, not measured against a bill.

## The model API

Measured against the live API on 2026-11-02, with Opus 5.5.

- **Every request streams.** The SDK refuses a call that does not stream above about 21,333 `max_tokens`, and thinking counts against that limit. A dropped stream is not retried, because the SDK retries only before a stream starts, so it ends the run with a next action. See [decision 0011](decisions/0011-stream-every-request.md).

- **Strict tool use is refused for the repo profile and for the facts.** The API answers `For 'object' type, 'additionalProperties: object' is not supported` for the open `args` dict in the profile, and `Schema type 'oneOf' is not supported` for the fact union. Rewriting `oneOf` as `anyOf` did not help on Haiku 5.5: the API then said the compiled grammar was too large. Tools with these schemas must be sent with `strict=False`, and code validation holds the guarantee.
- **A refusal ends the agent, with no retry on another model.** The server-side fallback needs the beta client, and Haiku 5.5, which the classifier uses, has no fallback at all. The agent stops with the reason `refused`. The category and explanation go to `model_call` and `debug.log`, and `AgentStopped` exposes the category, so false positives can be counted on the first real run. No live refusal has been seen yet, so this rests on the SDK's types.
- **An error result with no text is refused by the API** (HTTP 400). The agent loop sends a stand-in text, so a tool that fails silently does not end the run.
